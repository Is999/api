# 标准开发流程

此 skill 是主流程，负责调度专项 skill，但不替代专项 skill。

## 最高级实现准入门槛

业务正确、安全、数据完整性和资源边界不可退让；在此前提下，代码简洁、逻辑清晰、易阅读易维护是所有实现的最高优先级，不是功能跑通后的可选润色。实现必须达到专业资深的高级开发者标准，阅读和维护门槛以初级开发者也能轻松上手为目标：通过主流程、就近注释和测试理解已实现的需求与业务规则，定位修改及回归位置；不以资深开发者看得懂或测试通过替代。

- 编辑前：沿真实入口确认输入、业务规则、副作用和失败终态，找出当前项目同类实现；方案必须说明为什么需要保留每个新层级、状态、查询、事务和重试，不以未来扩展为理由预埋。
- 实现中：按业务顺序组织校验、分支和副作用，删除无职责转发及重复查询/判断；一个逻辑点一条就近短说明，方法头只说明职责与调用边界，禁止用集中长注释掩盖多个逻辑。
- 事务边界：不需要共同提交或一致性快照时不额外包事务；独立查询、校验、计算和整理前置，原子读写、锁定读取和提交重验保留，按 `$go-db-query-performance-guard` 核对行数、时间与锁等待，禁止无界大事务、长事务及事务内非数据库 I/O。
- 提交前：按 `$simple-code-guard` 逐项复核调用和 I/O，按 `$go-comment-style-audit` 核对方法内关键块的就近短注释；存在无法说明职责的包装、无原子性依据的事务、可复用而重复获取的数据或未解释的并发/失败边界时，判定未通过，不能以功能可用或测试为绿交付。
- 性能结论：写明减少的查询、往返、扫描或分配；宣称提升必须有同一输入、环境下的前后测量。不能以推测中的性能收益换取更难读的分支和调用，也不能删除正确性保护来缩短代码。

## 表达闸门

计划、实现说明、审查结论和交付记录不得用“简洁”“闭环”“同步相关内容”“必要时”“验证通过”“生产可用”等词代替动作和证据：

- 每项规则必须能回答何时触发、检查什么、执行什么、怎样判定通过、失败后怎样处理。
- 完成结论按需求类型对应证据：功能对应真实入口、调用链、副作用和同步面；文档与 Skill 对应消费入口、事实、引用和执行决策，两者都绑定最后一次修改后的适用验证。
- 无法给出触发条件的“必要时/按需”、无法列出对象的“相关内容”、无法给出命令与结果的“验证通过”均视为未执行。
- 实现质量以当前业务是否直接可读、规则是否单一、调用和资源边界是否有证据为准；简洁性执行 `$simple-code-guard`，方法内就近注释执行 `$go-comment-style-audit`。不得用“资深风格、没有 AI 痕迹”代替这些检查。

## 长任务止损闸门

出现以下任一情况时，按长任务执行：跨仓变更需要协调共享契约或发布、包含六个及以上可独立验收项、需要启动本地服务或浏览器完成端到端验证、预计连续执行超过 30 分钟。仅在两个仓库同步同一条文案不按长任务处理。

1. 开始编辑前记录里程碑、真实入口、预期结果、验证命令和状态；同一工作流只保留一个当前里程碑。用户澄清或纠正当前项时立即调整，新增独立需求列入后续项，明确替换目标时停止旧目标。
2. 单个执行循环最多持续 20 分钟，或最多连续进行三轮没有新增证据的工具调用。每轮必须至少产出一种新证据：有效代码差异、定位到的新事实、通过的检查或具有解除条件的明确阻塞；否则立即停止当前方法。
3. 同一失败在没有新证据时最多重试两次。第三次不得继续换参数盲试，必须记录错误指纹、已验证假设、替代方案和阻塞条件；替代方案仍失败时交付当前阶段结果并等待解除条件。
4. 长命令必须限制输出并尽快返回运行标识；单次等待不超过 60 秒，只有预计状态会变化时才继续等待。禁止长时间阻塞等待、重复读取无变化输出或对相同外部状态无限轮询。
5. 读取源码和日志使用 `rg`、定向行段和差异结果。已经确认且未变化的完整文件不得反复载入；日志只保留首个根因、关键上下文和最终结果，截图、原始响应和大段终端输出不得重复注入上下文。
6. 每个里程碑维护一份短证据快照：已完成项、当前项、最后新增证据、剩余项、阻塞和下一步。恢复长任务时先读取快照和最新差异，不从头重新发现已经确认的事实。
7. 修改后只先运行受影响范围的增量检查；全仓检查在里程碑收口或最终交付时运行一次。最后一次修改会使受影响的既有绿色结果失效，必须把对应状态退回“待验证”。
8. 两种独立处理方法均失败，或连续三轮没有新增证据时，触发强制止损。此时必须明确报告“阶段性已完成”“已完成但未验证”“被阻塞”或“未开始”，不得以继续复核掩盖无进展。
9. 长时间等待、扩大范围或进入下一里程碑前，先向用户报告当前状态、证据、剩余工作和风险。不得在缺少可见进展的情况下持续消耗执行时间和 Token。

上述限制是默认上限。只有用户明确要求持续监控，且外部状态确实会变化时，才允许越过单轮时限；仍需使用有界等待并保持阶段性报告。

## 阶段闸门

1. 入口闸门：先判断用户要求是分析、解释、复核、验证还是实现；前四类保持只读，不因发现问题自动获得修改权限。用户明确要求修复/更新或确认方案后才编辑；意图或边界不清时使用 `$requirement-intent-gate`。
2. 源码闸门：编辑前读取生效的 `AGENTS.md`，并用 `rg --files` 发现当前仓库实际存在的 AI 文档、代码路径、测试、路由、配置、契约和文档。
3. 诊断分类闸门：分析 bug、阻塞点或验证失败时，分栏输出“正常逻辑缺陷”“极端运行条件”和“验证环境阻塞”。依赖健康且普通输入/并发可触发错误行为的，归为正常逻辑缺陷；生产事件或主动故障注入已经执行到 Redis、MySQL、MQ、DNS、网络、磁盘或资源故障处理代码时，归为极端运行条件，并在该栏内标记代码处理符合预期还是存在无界阻塞/重试、误写数据、资源泄漏、伪成功、进程退出等韧性缺陷；验证原本要求依赖健康，但本机缺少依赖、工具或权限并在到达待测逻辑前失败时，归为验证环境阻塞。相同的 `connection refused` 必须按验证目标和实际到达的代码边界分类，不能只按错误文本判断。三栏逐项输出触发条件、证据、期望/实际行为、影响、代码责任和处理结论，禁止混合列举或合并计数。
4. 计划闸门：非平凡任务先说明已确认目标行为、源码证据、可能文件、非目标、风险面和验证命令。
5. 实现闸门：改动保持小而聚焦，优先使用当前仓库现有模式；遇到成熟通用能力、高风险基础设施或手写实现容易出错的场景，先检查现有实现和成熟依赖/框架。确需新增抽象、目录、依赖或框架时，说明必要性、收益、替代方案、影响范围和验证方式，并让开发确认后再落地。
6. SQL 闸门：只有当前任务触及 MySQL/SQL 时才启用。先区分完整初始化资产、运行时代码 SQL 和存量库一次性变更；优先 GORM 链式调用，原生 SQL 必须说明例外原因、索引、扫描范围、分页/批量、超时、并发和 DB 压力控制。
7. 数据库变更闸门：DDL/DML 变化直接更新仓库原始初始化基线，不新增碎片化迁移 SQL 或日常迁移版本；存量库 SQL 只放被忽略的 `data/sql-changes/<change-id>/`，交给 DBA/运维执行并确认未进入 Git。
8. 同步闸门：按源码变化和调用方搜索识别触发面，并建立同步影响记录。将 route、request/response、RouteMeta、权限/安全、业务码/i18n、配置、Model、完整初始化 DDL/DML、SQL/Lua、Redis Key、前端 wrapper/type、文档、测试和运维步骤作为发现清单，而不是固定填空表；每个被触发面记录源码依据、修改文件、验证结果和未覆盖路径。只有常见风险面容易被误判为已处理时才记录不适用及具体依据，禁止用一个“不适用”概括所有未检查项。
9. 领域闸门：按当前仓库真实技术面调用已安装专项 skill。Redis、配置/热加载、worker/队列、安全路由、数据库变更、前端 CI/hook 或兄弟仓库同步不存在时，不强行套用。
10. 可维护性闸门：逐个复核新增目录、接口、结构体、状态、分支、wrapper 和 helper，要求存在当前需求、真实调用方、稳定复用边界或故障证据；只转发参数且无校验、转换、事务、重试或依赖隔离职责的包装应内联。清理现有文件时先区分“生产已启用”“项目基础能力但当前未启用”“确认废弃无用”；没有业务调用方不能单独作为删除依据，仍承载稳定扩展契约、已有多实现、外部依赖隔离、共享约定、CLI/Make/测试/运维入口或明确职责与聚焦测试的基础能力必须保留并准确标注启用状态。新增或重构的稳定契约和关键逻辑按项目清单补中文注释。触及项目自有 YAML 时，每个固定字段核对 config struct/tag、默认值、normalize/getter、校验器、消费方和 reload 应用器，在字段正上方补同缩进中文注释；父节点不能代替子字段，动态 map 与第三方 schema 按 `$go-config-runtime-guard` 记录共享说明或排除证据。高风险或全仓库场景使用 `$go-comment-style-audit`。
11. 冻结闸门：最终复核前停止并发编辑，确认候选版本位于 worktree 还是 index。校验 index 的 hook 必须在最终暂存后运行；最后一次代码、配置、测试或文档修改会使此前结果失效，必须重跑受影响门禁。
12. 收口闸门：非平凡任务交付前使用 `$implementation-closure-review`；需要 staged 文件或运维交接时使用 `$release-handoff-guard`。复核需求闭环、命名、真实调用链、同步面、测试、跳过项和剩余风险。
13. 交付闸门：最终说明必须区分已完成、已验证、已交付待执行、已跳过、被阻塞和需后续处理，并说明新库初始化、DBA/运维 SQL、回填、缓存和补偿需求。

## 必留证据

每个实现任务都要留下足够证据，便于其他开发者复审：

- 已检查的源码事实：文件、函数、路由、文档、配置、SQL/log 片段或测试。
- 实现边界：改了什么、明确不改什么。
- SQL 证据：仅在任务触及 SQL 时说明 GORM 链式选择或原生 SQL 例外、索引依据、扫描范围、批量/分页上限、超时、并发和 DB 压力控制。
- 同步面：按源码识别当前仓库实际受影响的后端、前端、文档、配置、权限、安全、i18n、Redis、SQL/Lua 和测试；常见风险面若判定不适用，附调用方搜索或注册/配置依据。
- 验证：实际命令和结果；验证失败时使用当前仓库已安装且适配的专项 skill；跳过检查必须说明原因。
- 诊断类型：正常逻辑缺陷、极端运行条件和验证环境阻塞分栏记录；极端运行条件内再标记代码处理符合预期或存在韧性缺陷，没有某栏时明确写“未发现”。
- 验证快照：说明门禁针对 worktree 还是 index；不得用最后一次修改前的绿色结果证明当前候选版本。
- 长任务快照：记录当前里程碑、完成比例、最后新增证据、重复失败次数、剩余项、阻塞条件和下一步，避免恢复后从头分析。
- 仓库状态：每个触碰 Git 仓库都运行 `git diff --check` 和 `git status --short`。

## 完成判定

- `已完成且已验证`：需求项及实际同步面均达到验收条件；功能以真实入口、成功/失败终态和副作用为证据，文档与 Skill 以事实、引用及执行决策为证据，受影响的验证均在最后一次修改后完成并记录结果。
- `已完成但未验证`：实现与同步已完成，但明确命令因环境或权限未执行；必须列出未覆盖风险和补跑责任。
- `已交付待人工执行`：代码或本地 DBA/运维材料已准备，但生产 SQL、发布、缓存清理或重启仍需授权人员执行；不得写成已上线。
- `已跳过`：该面不存在或经源码证明不受影响；必须记录证据，不能用“无需处理”一句带过。
- `被阻塞`：缺少会实质改变实现的需求选择、权限、依赖或环境；说明已检查证据、影响和解除条件。
- `阶段性已完成`：当前里程碑已达到验收条件，但后续里程碑尚未开始；必须列出已完成范围、最后验证结果和后续清单，不能表述为整个任务已经完成。
- 全仓审查或注释补齐另需逐文件哈希与语义覆盖账本；未阅读、部分阅读和待验证不计入完成。只读审查以覆盖范围、发现证据和未验证项交付，不以修复所有发现作为擅自写入条件；静态零告警、代表文件或测试通过均不能证明所有 Bug 已处理。

## 专项路由

以当前仓库 `AGENTS.md`、`.agents/skills` 和实际文件树为准，只调用真实适配且已安装的专项 skill。缺失或不适配时按同样闸门手动执行并说明。
