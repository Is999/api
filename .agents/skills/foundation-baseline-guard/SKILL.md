# API 基础骨架保护

## 本项目边界

本仓库承担前台 API 运行框架。基础骨架包括进程启动与停机、配置和资源生命周期、ServiceContext、HTTP/RPC 路由与中间件、登录态与主体识别、路由安全、统一响应与错误、数据库/Redis/MQ 通用能力、collector/worker 底座、构建和 CI。

领域 handler、logic、service、repository、model、collector、worker、业务码、业务配置、业务 SQL、接口文档和测试属于业务扩展。业务实现必须沿用现有鉴权、请求上下文、错误信封、超时和资源治理能力。

## 编辑前判定

开始修改前记录当前提交、业务来源、共享契约调用方和允许范围，并把文件分为业务变更、业务接入变更、基础骨架核心变更。

本仓库自身是 API 基础骨架来源时，框架演进仍属于核心变更；必须检查后台调用方、站点网关、消费者和下游 API 项目的兼容性。

## 核心变更确认

核心代码默认只读。已复现的框架缺陷、安全/稳定性/数据一致性问题、现有扩展点无法承载需求，或开发人员明确要求演进基础框架时，才可以提出修改。

实施前必须向开发人员说明并等待明确确认：

```text
问题与复现证据:
领域层或现有扩展点不可解决的原因:
拟修改文件、符号和调用链:
对 API 契约、认证安全、数据访问、消费者和下游项目的影响:
替代方案及取舍:
测试、灰度、回退和契约同步方案:
```

一般性的业务实现要求不构成核心代码修改授权。明确同步某个基础版本时，只授权已核对的来源差异。

## 实施与复核

- 禁止绕过统一鉴权、路由安全、请求上下文、错误信封和超时边界建立业务捷径。
- 禁止把领域常量、站点特例、临时兼容分支或只转发参数的包装写入公共层。
- 旧业务迁入时保留领域规则和最终副作用，但按当前 API 调用链、依赖注入和并发边界重新接线。
- 修改后逐项解释核心路径差异，并验证 HTTP/RPC、认证、共享契约和资源关闭路径。
- 最终记录业务变更、接入变更、获批核心变更、契约同步面、实际验证命令和回退方式。
