# 简洁代码护栏

本 skill 是所有代码落地的首要质量验收门槛，不是只在重构时使用的建议清单。下列调用、业务规则、注释和性能边界有任一项不成立时，即使功能测试通过，也不能判定实现完成。

先保持请求/响应、错误、事务、鉴权、幂等、重试、状态机和资源释放语义，再删除没有当前需求、真实调用方、稳定复用边界或故障证据的包装、接口、状态、分支和重复实现。只解决当前需求、源码、调用方或故障证据已经证明的问题，不为假设场景预埋复杂度。

业务正确、安全、数据完整性和资源边界不可退让；在此前提下，代码简洁、逻辑清晰、易阅读易维护是所有实现的最高优先级，不是功能跑通后的可选润色。实现必须达到专业资深的高级开发者标准，让初级开发者通过主流程、就近注释和测试理解需求规则、定位修改与回归；不以行数最少、抽象数量或“资深风格”代替验收：

- 主流程按业务顺序展开，初级开发者能沿准确命名、就近注释和测试理解校验、状态变化、最终副作用与失败结果，定位常规修改及回归位置；不依赖无职责 wrapper/helper 跳转或作者口头解释。
- 同一业务域沿用已存在的命名、分层、错误返回和测试写法；不新增模板化分层、同义状态、泛化参数或只服务假设扩展的配置。
- 每个抽象都有当前调用方和明确职责；接口有外部依赖、真实替换点、依赖环或多个实现，helper 收口稳定重复规则或显著缩短主流程。
- 一个业务规则只有一个权威实现；重复条件、重复转换、魔法字符串和失效兼容分支已删除或收口。
- 公共基础设施依赖由服务启动阶段统一创建、校验并注入后，业务入口不得重复添加没有新语义的 `nil` 判空；先检查启动装配是否对缺失依赖拒绝启动，再删除只重复同一保证的入口防御。
- 名称表达业务对象、动作、状态或单位；职责变化后没有保留旧名，不能用 `Manager/Helper/Common/Info` 掩盖多个职责。
- 保留的 goroutine、锁、事务、幂等、重试、超时、取消和资源释放必须各有调用方或故障场景，并由对应成功、竞争、超时/取消和失败恢复测试覆盖；减少文件数、函数数或代码行数不得删除这些已验证边界。

## 读取项目边界

1. 读取从工作区到目标文件生效的全部 `AGENTS.md`；最近规则优先。
2. 只读取当前项目对应参考：`references/admin.md`、`references/api.md` 或 `references/admin-vue.md`。
3. 从真实入口追到最终副作用、状态变化和测试，不凭文件名判断是否可删或可简化。

## 简化顺序

先把候选项分为三类：

- **生产已启用**：能从 route、CLI、Worker、Scheduler、Collector、配置装配或框架回调追到最终副作用。
- **基础能力但当前未启用**：暂时没有业务调用方，但仍提供稳定扩展契约、承载两个及以上已有实现、隔离外部依赖、维护跨服务共享约定，或作为 CLI、Make、测试、生成、部署、运维入口；必须有明确职责、聚焦测试或接入文档。此类能力保留，但不得描述为生产已启用。
- **确认废弃无用**：静态引用、运行时注册、反射、框架回调、导出契约、CLI/Make、测试、文档和运维入口均不存在或已有权威替代；不再承载独立职责，删除不会减少现有功能、扩展契约、测试工具或部署能力。

“没有当前业务调用方”只能证明未启用，不能单独证明无用。简化时按以下顺序处理：

1. 只删除“确认废弃无用”的代码、兼容逻辑、重复实现和不可达分支；删除后重跑适用包测试与构建，按影响扩大验证；失败时只撤销本轮删除及配套改动并重新判定，不覆盖用户已有修改。
2. 内联只转发参数或调用下一层且没有业务语义的包装，缩短主调用链。
3. 使用提前返回和直接条件简化嵌套，合并表达同一规则的重复判断。
4. 保留具体类型；只有隔离外部依赖、解除真实依赖环或存在多个实现时才增加接口。
5. helper 仅用于收口已有重复业务规则、隔离 I/O/协议边界，或显著缩短真实主调用链；必须列出调用方、独立职责和提取前后的路径。单调用方但职责明确的业务块可以提取；只有一行转发、仅拆出短判断或名称比逻辑更难理解时不提取。
6. 命名直接表达业务动作和状态；职责变化时同步改名。

### 基础设施依赖判空

审查 `DB`、Redis、MQ、对象存储、指标、锁、任务队列等公共依赖时，先沿 `bootstrap/startup -> ServiceContext -> handler/logic/worker` 核对初始化、校验、注入和关闭链路：

- 依赖操作已经统一经过现有 gateway、manager 或 helper，且该入口会在首次解引用前校验依赖并返回相同错误类别时，由该入口作为权威判空边界；调用方不得再次检查同一指针。只有调用方需要降级为成功、转换业务码、跳过副作用或补充不同安全语义时才保留前置判断。
- 启动阶段已经创建并验证、缺失即拒绝启动的核心依赖，业务入口中的同一 `nil` 判空属于候选冗余；删除前必须确认该入口不会被迁移命令、测试、CLI、特殊装配或外部扩展直接绕过启动链路。
- 可按配置启用的组件、允许降级或回源的缓存、健康检查、资源关闭、测试构造和迁移/CLI 装配不属于无效重复判断；这些判断分别表达启用状态、运行时降级、诊断或资源生命周期，必须保留。
- 依赖对象非空不代表运行时可用。Redis、MySQL、MQ 等在启动后断连时应保留调用错误、超时、取消和重试边界，不能用删除 `nil` 判空替代真实连通性处理。
- 多个入口重复检查同一个可选依赖时，优先把“是否启用/是否可用”的规则收口到已有 ServiceContext 或组件能力，不新增只返回布尔值的泛化 helper；若收口会改变测试或外部装配契约，先记录影响并保持现状。
- 删除判空后必须检查成功、缺失依赖、运行时断连、超时/取消和关闭路径，并运行最后一次修改后的归属包测试及直接调用包测试。

## 正确性边界

- 默认保持外部可观察行为、返回值、错误、事务、鉴权、幂等、重试和状态机语义；需求明确要求改变时除外。
- 锁、租约、原子状态迁移、超时、取消、幂等和迁移互斥如果对应真实并发或故障窗口，属于必要业务逻辑，不能作为“理论防御”删除。
- 删除前必须先完成三分类。只有旧协议、旧字段或双轨兼容已确认没有静态/运行时/外部调用方，不承载基础扩展或共享契约，且删除不损失测试、部署和运维能力时，才删除无必要的迁移层。
- 不降低项目注释、命名、接口同步和验证要求。简洁用于控制表达，不是省略业务边界的理由。
- 不用大范围重构掩盖局部问题，不顺手修改任务外代码。

## 性能判断

- 先确认热路径、数据规模、调用频率和外部 I/O，再决定优化重点。
- 热路径优先减少 DB/Redis/MQ 往返、全量扫描、重复序列化、无界分配、对象创建和字符串拼接。
- 不需要共同提交或一致性快照时不额外包事务；实际 SQL、批次与 Hook 决定原子性，解析、校验、哈希、整理和独立查询前置，锁定读取及提交条件重验保留。
- 事务内只留数据库原子操作，不做 HTTP/RPC、Redis/MQ、文件处理、等待或退避重试；按 `$go-db-query-performance-guard` 检查行数、执行时间与锁等待，允许独立提交才拆小批，不能靠破坏原子性或转后台掩盖大事务、长事务。
- 同一请求已取得且仍有效的数据直接复用，不重复查询或判断；数据可能被并发改变时，采用条件写入、CAS 或必要重验，并在对应位置说明失效窗口。
- 已知容量可预分配，已有解析结果可复用，有明确上限时可批量；冷路径不以难读的微优化换取理论收益。
- 性能优化不得放宽数据边界、错误处理、并发正确性或资源释放。
- 宣称“性能提升”前必须记录同一输入和环境下的前后基准、trace、执行计划或指标；只有静态推理时，结论限定为减少了哪一次 I/O、哪段扫描或哪类分配，并明确尚未量化。
- 数据库路径至少记录索引、预估扫描/返回行数、batch、timeout 和 concurrency；Redis/MQ 路径至少记录往返次数、Key/消息基数、批量上限和失败重试边界。

## 执行与交付

1. 写明不变的业务语义、当前真实问题和非目标。
2. 列出入口、主调用链、状态或副作用和现有测试，识别最长跳转与重复点。
3. 先分类并取得删除证据，再清理“确认废弃无用”项；选择解决问题的最小差异，不先建框架。
4. 核对调用方、配置、SQL/Lua、指标、文档和测试，确保没有失效入口或半成品。
5. 最后一次修改后运行项目参考中的验证，并检查 worktree/index 和仓库状态。

审查问题逐项报告当前证据、实际影响、最小改法和验证方式。完成结论必须列出：保持或改变的外部行为、仍存在的跳转和抽象、生产入口到最终副作用的链路、最后一次修改后的验证结果、阻断项，以及迁移、回填、缓存失效或补偿需求；禁止只写“已简化”“可维护性已提升”。
