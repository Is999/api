# 部署发布指南

## 目标

本文约束 `api` 前台 API 的上线、配置、数据库变更交付和生产观测流程。后台管理和运营任务由 `admin` 承担。

## 部署前检查

上线前确认：

1. 最后一次源码修改后执行 `make ci` 且退出码为 `0`；环境缺少完整门禁依赖时，至少执行格式检查、`go test ./...`、`go build ./cmd/api`、`go build ./cmd/migrate`，逐条记录退出码、跳过项和 CI 补跑责任。
2. 初始化或补齐未登记资产前已核对目标库、已有表和 dry-run 计划；修改已有结构或数据时准备经评审的 DBA/运维变更单，本地 SQL 不进入 Git。
3. 初始化资产中的 `sys_config` 使用未加前缀的固定表名，以保持共享数据库结构兼容；当前 API 运行期不读取该表。其它前台业务表名必须与 GORM `TableName()` 和完整初始化 DDL 逐字节相等，不得残留临时、日期或迁移后缀。
4. `etc/config.yaml` 从环境模板生成且权限必须为 `600`，该文件禁止纳入 Git；`app_id` 唯一，`app_key` 与 `jwt_secret` 由 CSPRNG 生成、不同于样例值并通过启动长度/格式校验。`trusted_proxies` 逐项对应实际 LB/Ingress 地址或网段；已有敏感数据后变更 `app_key` 必须配套密钥版本迁移、历史回填和回滚方案，不能直接热切。
5. `snowflake.redis.enabled=true` 已启用，且同一套 `api/admin` 部署使用同一 `snowflake.redis.scope`；同一业务唯一域必须使用相同 `NextID(namespace)` 和 `snowflake.redis.namespaces.<namespace>.node_count`，当前 `user` 使用 10 个 node_id。滚动停机后必须允许旧 node_id 租约保留完整 `lease_seconds` 隔离窗口，节点池必须预留轮换容量，不得手工删除租约 key 加速复用。仅手工强管控场景允许改用全局唯一的 `snowflake.worker_id`；如启用 `snowflake.segment`，确认对应 namespace 的 `scope/step/prefetch_threshold` 已压测。
6. 生产只使用唯一规范值 `Mode=pro`，已启用登录限流；开放注册时已启用注册限流。其它模式值、大小写或首尾空白在启动期直接拒绝。
7. 已配置非样例 `ops.config_reload_token` 和独立 `internal_server`；跨主机监听绑定明确私网 IP 并通过 mTLS 证书校验。合法 Ops HMAC 请求成功，错误 token、过期 timestamp 和重复 nonce 均失败；Redis 不可用时防重放请求失败关闭。
8. 公网监听器的 `/api/live` 返回 HTTP 2xx 且不访问外部依赖，`/api/ready` 仅在所有 enabled 组件 ready 时返回 2xx；公网监听器的 `/api/metrics` 必须返回 404，目标 Prometheus 只能从独立内网监听器抓取指标，内网监听器由安全组、NetworkPolicy 或 mTLS 限制来源。
9. 重新生成后端 route security manifest 并与 `docs/site/route_security_manifest.json` 比较为零差异；前端安全向量逐 alias 比较 method/path、签名/加密点路径、空数组语义、字段大小和密钥版本，未知路由显式拒绝而不套用通用 `*` 策略。
10. 启用 Lark 运行异常告警时，`webhook_url` 与 `webhook_url_ref` 必须二选一，`secret` 与 `secret_ref` 最多选择一个；推荐由受控引用文件注入，并发送一条不含 token/密钥/请求体的测试卡片。

## 构建

```bash
make ci
make package VERSION=20260605
```

没有 `make` 时可按以下命令完成格式化、测试和二进制构建；这些命令不包含完整 CI 门禁或发布打包：

```bash
gofmt -w $(find . -name '*.go' -not -path './vendor/*')
go test ./...
go build -o bin/api ./cmd/api
go build -o bin/api-migrate ./cmd/migrate
```

发布产物至少包含：

- `bin/api`
- `bin/api-migrate`
- `dist/api-<version>.tar.gz`
- `etc/config.yaml`
- 必要的证书、密钥和运行期配置文件

仓库提供的部署模板：

- `deploy/docker/Dockerfile`
- `deploy/systemd/api.service`
- `deploy/integration/docker-compose.yml`

`make package` 只收录 `PACKAGE_FILES` 声明的二进制和公开模板；环境配置与密钥单独交付。Docker 构建依赖根 `.dockerignore` 排除本地配置、密钥和数据目录，不得删去过滤规则或反选恢复敏感文件。集成 MySQL 仅绑定宿主机回环地址。

## 数据库初始化与变更交付

- 数据库唯一基线为 MySQL 8，与初始化资产的 `utf8mb4_0900_ai_ci` 和集成环境一致；不维护 MySQL 5.x/MariaDB 方言兼容。GORM 不再自动执行无 deadline 的版本查询，启动连通性仍由显式 5 秒 PingContext 探测；这不等于所有驱动 I/O 都具有相同超时。
- `migrate-status`、`migrate-dry-run` 只读；`migrate-bootstrap` 显式授权执行未登记资产，允许非空库和部分登记续跑。
- API 只读写 `api_schema_migrations`，Admin 只读写 `admin_schema_migrations`；两套工具可管理同一主库，均以 `app:schema-migration` 串行保护状态读取和资产执行。
- 本仓已登记且名称、资产、checksum 一致的项跳过；本仓元数据冲突或清单外版本在执行 SQL 前拒绝，不覆盖或伪造登记，也不读取或自动搬迁通用 `schema_migrations`。
- 同库初始化须执行两套清单，顺序不限；Admin 用户管理依赖 API 清单中的 `user` 和四张 `user_identity_*` 表，不能仅执行 Admin 迁移后就交付用户管理功能。
- 六份 API 业务资产均为 `CREATE TABLE IF NOT EXISTS`，无 seed；补缺表不修改已有列、索引或用户数据，不能替代结构升级，也不向 `defaultMigrationSpecs` 追加需求级版本。
- 需求涉及 DDL/DML 时，代码仓库直接更新原始初始化资产；开发另在被忽略的 `data/sql-changes/<change-id>/` 准备存量库实际需要的增量 SQL。
- 发布工单必须包含 SQL SHA-256、目标实例与库表、当前结构依据、执行顺序、锁和扫描风险、停止条件、验证语句及恢复或补偿方案；DBA/运维使用命令行受控执行。
- 本地 SQL、回填、修复和补偿文件不得提交或暂存；执行记录、受影响行数和验证结果保留在工单或 DBA 平台。

初始化资产清单、重复执行边界、存量库变更包结构和 DBA 执行要求只在[数据库初始化与变更交付治理](角色文档/运维/数据库迁移治理.md)维护；部署指南不复制清单，避免版本和命令双处漂移。

业务用户按量拆表运行边界：

1. `shard_no = CRC32(十进制 user.id)%1024` 固定不变，Admin/API 根据相同启动配置在应用内选择用户物理表。
2. `user.route_shard_count` 只接受 `1/2/4/.../1024`；身份表只保存稳定的 `user_id/user_shard_no`，不保存物理分片数量。
3. Admin 使用 `cmd/tableshard` 创建目标表，嵌入 Ghostferry 在线复制历史行并持续追踪 ROW binlog。
4. 全量完成且增量接近追平后，入口短暂排队写请求，停止 Admin/API/Worker 并排空事务，再放行最终追平和内联校验。
5. 复制成功并生成本轮 `verified-file` 后，同步修改 Admin/API 的 `user.route_shard_count`；发布流水线必须比较最终渲染值，确认一致后再重启。
6. 失败时保持旧配置并清空未切流目标表后重跑；至少观察一个业务峰值和备份周期后，才小批清理旧表已迁移桶。

该路线不部署额外 Proxy 或 CDC 服务。完整命令、权限、校验和回滚边界见 Admin 同名分支的《库表路由规范》。

## 启动期硬校验

服务启动会在进入运行态前校验以下风险：

- `jwt_secret` 长度过短。
- Redis 地址为空或连接池大小无效。
- 雪花 Redis 租约参数不安全，Segment 号段参数非法，或手工 `snowflake.worker_id` 缺失、越界。
- `user.route_shard_count` 不在 `1/2/4/.../1024` 允许档位内。
- 认证密码最小长度低于安全下限。
- 登录/注册限流窗口、次数或锁定时间超过可控范围。
- Collector 未启用，或 `collector.tasks.auth.security.topic` 不是 `api_collector_auth_security_events`。
- 运维白名单配置公网 IP/CIDR。
- 生产环境使用占位密钥、未配置运维令牌、关闭登录限流或跳过 Redis TLS 证书校验。
- `security.secret_key.versions` 的 AES/RSA 文件引用仅接受不超过 64 KiB 的普通文件（允许指向普通文件的符号链接）；FIFO、设备和目录在读取前拒绝，超限文件不截断使用。相对路径仍以进程工作目录解析，空内容、首尾空白修剪及 PEM 校验保持原规则；材料更换后需重启。该文件读取实现面向当前 Darwin/Linux 目标，不覆盖内网 mTLS CA 等其它文件入口。

## 运行

```bash
./bin/api -f ./etc/config.yaml
```

配置热加载只刷新运行期配置，不重建 HTTP 监听、MySQL、Redis、OTLP 等启动期连接。启动期配置变化会在热加载状态中标记为需重启。

主文件和外置文件分别从单次读取的内容解码并计算指纹，版本由这份指纹派生；读取后发生原子替换时，下一轮仍会发现新内容。发布配置优先原子替换，读取期间检测到原地改写会拒绝本轮候选，并在下一轮重试。

`alert.lark` 发送端配置也属于启动期依赖，热加载变更只记录需重启，不在线替换 webhook 或签名密钥。

## 观测与告警

发布后至少确认：

- `/api/live` 返回成功。
- `/api/ready` 返回 HTTP 2xx，响应中已启用的 MySQL、Redis、Collector 均为 ready；未启用组件明确标记 disabled，任何 enabled 组件为 failure 时发布不通过。
- `/api/metrics` 可被 Prometheus 从内网监听器抓取，公网监听器访问同一路径返回 404。
- 日志中可通过 `trace_id`、`route`、`uid`、`app_id` 关联一次请求。
- ID 生成指标 `api_idgen_generated_total{biz_type,strategy,result}` 有基线数据；启用 Segment 时同时观察 `api_idgen_segment_remaining{biz_type}`、`api_idgen_segment_allocations_total{biz_type,result}` 和 `api_idgen_snowflake_lease_events_total{biz_type,event}`。
- Collector Kafka 投递指标 `api_collector_kafka_publish_events_total{result}` 有基线数据。
- 认证限流清理指标 `api_auth_rate_limit_cleanup_failures_total{action}` 正常保持不增长；递增时检查 Redis 写链路，限流 Key 依靠自身 TTL 回收，不执行全库扫描。
- 如启用 `alert.lark`，启动失败、平滑停止失败、配置热加载失败和 Collector 投递失败会发送 Lark 运行异常卡片。
- 认证安全细分指标由 Admin Kafka 消费侧按 `auth.security` 的 `action/reason/app_id/category` 聚合；`route` 仅保留在事件中辅助排障。
- Prometheus 可加载 `docs/prometheus/api-alerts.yml`，并按生产基线调整阈值。
- Grafana 可导入 `docs/grafana/api-dashboard.json` 观察 API 基线和 Collector 投递状态。

详细 PromQL 参考 [认证安全指标与告警](角色文档/后端开发/认证安全指标与告警.md)。

## 发布流程

容器或进程托管平台的终止宽限期不得低于 30 秒。服务收到信号后最多等待 5 秒排空 HTTP 请求，再为基础设施关闭保留 20 秒，并在 29 秒触发框架强退保护。HTTP、热加载、连接池、tracing 或日志关闭任一失败都会在可用日志通道记录并使进程返回非零退出码，发布系统不得把该实例判为正常下线。

1. 合并代码并完成测试。
2. 完成初始化或未登记资产续跑并核对实际结构；已有列、索引或数据需要变更时，按 DBA/运维变更单执行本地 SQL，并完成结构、数据和指标验证。
3. 发布新二进制和配置。
4. 确认 `/api/ready` 返回 HTTP 2xx，所有 enabled 组件为 ready，disabled 组件未被误报为 failure。
5. 对登录、刷新 token、用户信息、系统配置读取执行低风险冒烟。
6. 若启用签名或加密，使用前端安全清单覆盖至少一个签名接口和一个加密接口。
7. 观察 10 到 30 分钟认证安全指标、错误日志和 Redis session 写入。

## 回滚

1. 摘除异常实例或回退流量。
2. 恢复上一版本二进制和配置。
3. 确认 `/api/ready` 返回 HTTP 2xx；测试账号可以登录并生成 session，刷新后旧 token 不能再次刷新，Redis 中旧 session/index 按轮换语义失效且新 session 可验证。
4. 如果本次包含数据库变更，按 DBA/运维变更单确认是否需要备份恢复或前向补偿。
5. 观察 `security_config`、`token`、`auth` 分类指标，确认异常恢复到基线。
