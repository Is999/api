# 前端安全策略同步与联调指南

本文约束前端如何消费 API 路由的签名、加密和访问链策略，并给出后端变更、快照更新、前端落地、测试和故障定位的完整流程。当前工作区没有独立前台仓库时，`docs/site/route_security_manifest.json` 仍是必须维护的稳定交接资产。

## 1. 权威来源

```text
module RouteSpecs
  -> route contracts / security chain
RouteMeta + RouteSecurityPolicies
  -> DefaultRouteSecurityManifest()
  -> docs/site/route_security_manifest.json
  -> frontend route policy
```

| 层 | 权威入口 | 职责 |
| --- | --- | --- |
| 路由事实 | 各模块 `RouteSpecs()` | alias、method、path、access chain |
| 字段安全 | `RouteSecurityPolicies` | 请求/响应签名和加密点路径 |
| 后端派生清单 | `DefaultRouteSecurityManifest()` | 合并路由与字段策略，执行一致性校验 |
| 仓库快照 | `docs/site/route_security_manifest.json` | 给前端、评审和漂移测试使用 |
| 协议向量 | `internal/security/testdata/security_vectors.json` | 签名串、编码、加解密和点路径跨语言一致性 |

前端不能从接口文档文本自行推导安全策略，也不能按 URL 前缀设置通用 `*` 规则。接口文档用于人读，manifest 用于机器同步；防漂移测试必须逐 route alias 比较签名字段、加密字段、密钥版本和字段大小限制，任一缺失、多余或顺序语义差异都使测试失败。

## 2. 清单字段语义

前端按 `alias + method + path` 精确匹配。path 参数遵循后端清单输出的规范路由，不对未知路径做模糊继承。

### 2.1 chain

| chain | 前端行为 |
| --- | --- |
| `none` | 不进入前台签名、加密或 JWT 安全链 |
| `public` | 按字段策略执行签名/加密，不附加登录态要求 |
| `auth` | 按字段策略执行，并携带当前有效登录态 |
| `internal` | 不由公网前台调用；只供受信任内网运维客户端 |

### 2.2 签名字段

- `requestSign=null` / `responseSign=null`：该方向关闭签名。
- `requestSign=[]` / `responseSign=[]`：签名已启用，但不拼业务字段；仍按协议签 `appID`、`traceID`、`timestamp` 等基础材料。
- 非空数组：复制字段列表后按字段名 ASCII 升序生成 `v2` UTF-8 长度前缀签名串；点路径读取最终传输值，组合模式下该值为密文。
- 清单快照保留后端原始数组顺序用于漂移比较；签名串使用排序后的副本，不得增删字段或把空数组误认为关闭。

### 2.3 加密字段

- `requestCipher` 只允许请求体中声明的字段。
- `responseCipher` 点路径相对响应 `data` 读取。
- `X-Cipher` 只能携带当前路由清单允许的字段列表，不能使用 `cipher` 整包模式。
- 组合模式下每个 `requestCipher/responseCipher` 点路径同时存在于对应签名字段；客户端请求先加密再签名，响应先验签再解密。
- 加密字段的 `json:` 前缀只控制 JSON 编解码；例如 `json:payload` 在签名列表中写为真实路径 `payload`，不能写成 `json:payload`。客户端先对 `payload` 的密文验签，再按 JSON 解析明文；数字需使用无损解析或由业务契约以十进制字符串承载。当前内置路由未使用该前缀。

### 2.4 体积与数量边界

- 单接口参与签名或加密的字段最多 8 个。
- 普通字段最大 4 KiB，`json:` 小对象最大 8 KiB。
- 安全中间件读取请求体最多 64 KiB。
- 大表单、大对象、上传内容、分页列表和统计集合不得默认整体签名或加密，应拆字段或使用专用传输流程。

## 3. 前端策略实现

前端安全层应提供一个纯函数：输入 method、实际 path 和 manifest，输出当前路由策略或“无策略”。推荐规则：

1. method 规范化为大写。
2. path 去除 query，但保留与后端路由匹配相关的 path 参数结构。
3. 只匹配清单条目；未知路由返回空策略并由调用方决定是否允许发起。
4. `internal` 路由在公网构建中直接拒绝调用。
5. 请求先按 `requestCipher` 加密字段并设置准确 `X-Cipher`，再对最终密文字段生成签名。
6. 响应收到后先按 `responseSign` 对密文验签，再按 `X-Cipher` 解密，最后交给业务解析。
7. 任何未知签名算法、字段越界、点路径缺失或验签失败都失败关闭。

不要把 manifest 合并进人工维护的大型 switch；应保留可比较的快照或生成产物，并对未知路由、空数组和 null 写单测。

## 4. 后端修改流程

### 4.1 新增或改路由

1. 在模块 `RouteSpecs` 更新 alias、method、path、RouteMeta、接口文档和 chain。
2. alias 被多个位置复用时，先更新 `internal/routealias`。
3. 在 `RouteSecurityPolicies` 声明四类字段策略；没有前台安全字段也要明确 nil/空数组语义。
4. 更新接口文档 `### 安全字段`，写清每个方向是否关闭、基础头签名或具体字段。
5. 更新 `route_security_manifest.json`，与后端派生清单逐项比对。
6. 通知前端同步 route policy；method/path/alias 变化视为破坏性契约变更，必须协调发布顺序。

### 4.2 修改协议或点路径

1. 先更新后端协议实现和安全向量。
2. 只保留当前唯一协议向量，旧算法、旧头值和双读分支必须直接删除。
3. 同步前端测试向量副本并通过跨语言测试。
4. `X-Key-Version` 只做当前稳定/灰度密钥选路，不用于选择旧算法或旧密文协议。

## 5. 快照更新与校验

快照更新后必须检查：

- 条目数量与后端默认路由集合一致。
- alias、method、path 唯一且稳定。
- `chain` 与 RouteMeta 访问边界兼容。
- `requestSign/requestCipher/responseSign/responseCipher` 与接口文档逐字段一致。
- `responseCipher` 是 `responseSign` 的受控子集。
- `internal`/`none` 没有意外继承前台字段策略。
- 删除的路由已从快照、文档和前端策略清除。

后端运行：

```bash
go test ./internal/handler ./internal/security
```

测试会校验快照与 `DefaultRouteSecurityManifest()` 一致；不要手工修改测试期望来掩盖真实漂移。

## 6. 前端同步流程

1. 拉取同一候选版本的 `route_security_manifest.json`。
2. 比较新增、删除、method/path、chain 和四类字段策略。
3. 更新 route policy 或生成产物，保持清单快照顺序；签名串仍按字段名 ASCII 升序编码。
4. 更新请求/响应 TypeScript 类型，确保受保护字段名称和层级一致。
5. 同步 `security_vectors.json` 并运行签名、加密和组合模式单测。
6. 覆盖 null、空数组、未知路由、未知算法、字段缺失、字段超限、错误密钥和灰度密钥。
7. 对真实接口做小范围联调，保留 traceId、请求头、脱敏字段列表和业务码。
8. 前后端在同一联调候选中同步当前唯一协议；任一端仍发送旧头值或旧密文时停止交付。

前端日志不得打印密钥、AES 明文、RSA 私钥、完整 token 或受保护字段明文。排障只记录 alias、method、path、算法、密钥版本、字段名、traceId 和失败阶段。

## 7. 联调检查表

| 场景 | 预期 |
| --- | --- |
| 未知路由 | 返回无策略，不自动套用 `*`/`cipher` |
| `requestSign=null` | 不发送请求签名 |
| `requestSign=[]` | 发送基础头签名，不拼业务字段 |
| 请求加密 | `X-Cipher` 只列 `requestCipher` 允许字段 |
| 响应组合模式 | 先按密文点路径验签，后解密 |
| `chain=auth` | JWT/session 与字段安全链同时通过 |
| `chain=internal` | 公网前端拒绝调用 |
| 签名算法未知 | 客户端和服务端都失败关闭 |
| payload 超限 | 返回稳定 `security_payload_too_large` 类业务码，不扩大限制绕过 |
| 灰度密钥 | 双方使用相同版本路由和灰度规则 |

## 8. 故障定位

### 8.1 请求缺少签名

1. 确认实际 method/path 命中清单。
2. 查看 `requestSign`：`null` 表示关闭，空数组仍需基础头签名。
3. 核对 appID、traceID、timestamp 和密钥版本是否完整。

### 8.2 验签失败

- 核对签名算法只为短码 `R` 或 `H`，加密算法只为 `R` 或 `A`。
- 比较安全向量中的 UTF-8 字节长度、字段顺序、null/空值和点路径序列化。
- 检查客户端是否先加密并对最终密文签名；服务端不会在验签前解密。
- 确认时间戳、traceID、appID 和密钥版本没有被网关改写。

### 8.3 请求解密失败

- `X-Cipher` 是否包含未授权字段或缺少实际密文字段。
- AES-GCM 的 HKDF info、随机 nonce、AAD、标签拼接顺序，或 RSA-OAEP-SHA256 的 label、分块与密钥版本是否与当前 appID 一致。
- 字段是否超过大小限制，是否把大对象误用 `json:`。

### 8.4 响应验签失败

- 响应头是否包含 `X-Signature`、`X-Trace-Id`、`X-Timestamp` 和必要版本信息。
- 客户端是否在解密前先按密文 `responseSign` 点路径验签。
- 清单字段层级与响应 `data` 是否一致，空数组是否被误判为关闭。

### 8.5 `security_payload_too_large`

先减少受保护字段、拆分大对象或改用专用上传/异步接口。只有评审记录同时给出无法拆分的协议原因、字段数量与最大字节数、峰值并发、单请求与总内存计算、超限失败业务码以及压测结果，才能调整上限；单个接口不得直接放大全局安全中间件的请求体或响应缓冲边界。

## 9. 发布与回滚

发布前：

- 后端路由、安全快照、接口文档和安全向量属于同一提交。
- 前端 route policy、类型和向量测试基于同一快照。
- 不保留历史协议兼容窗口，前后端同一候选必须使用同一协议向量。
- 灰度环境验证登录、刷新、资料读写和至少一个加密响应。
- 监控能按业务码、route、appID、密钥版本和失败阶段聚合，但不记录敏感明文。

回滚时必须成对回滚协议、manifest 和前端策略。只回滚后端字段策略可能导致新前端继续发送服务端不认识的 `X-Cipher`；只回滚前端可能导致服务端要求签名而客户端不发送。

## 10. 交付证据

每次安全策略变更至少附：

- 变更路由和四类字段策略的 diff。
- 更新后的 manifest 与安全向量。
- 后端 `go test ./internal/handler ./internal/security` 结果。
- 前端安全单测、typecheck 和代表性联调结果。
- 旧协议删除证据、同一候选联调顺序、灰度、回滚和密钥轮换说明。
