# AI 开发规范

本文档是 AI 参与 `api-go` 开发时的项目级质量标准，适用于功能实现、问题修复、重构、测试、配置、SQL、脚本和文档。目标是在保持前台服务独立边界的同时，与 `admin-go` 共享一致的工程风格、安全契约和生产门槛。

## 使用方式

- 根目录 `AGENTS.md` 是短入口，负责声明不可跳过的流程、skill 和验证命令。
- [AI 开发提示词](角色文档/后端开发/AI开发提示词.md)是可复制的任务入口，只保留高频硬约束。
- 本文维护完整项目规范；遇到细分领域时，再读取对应专题文档和 skill reference。
- 用户最新明确要求优先，但不能绕过认证安全、数据完整性和诚实交付边界。

## 最高优先级：专业实现、低门槛维护

业务正确、安全、数据完整性和资源边界不可退让；在此前提下，代码简洁、逻辑清晰、易读易维护是所有实现的最高优先级，不是功能跑通后的可选润色。

- 实现水平必须达到专业资深的高级开发者标准：命名准确、风格统一，业务规则单一，主流程直接，不保留无职责包装、重复查询或无依据的事务。
- 阅读和维护门槛以初级开发者也能轻松上手为目标：具备项目语言基础后，应能沿主流程、就近注释和测试，通过代码理解已实现的需求、业务规则、关键分支与失败策略，定位修改及回归位置，不依赖作者口头解释或隐含约定。
- 评审每条改动链路时，从源码指出入口、业务步骤、数据副作用、失败结果和修改后的验证入口；如果必须猜测隐含状态、穿过无职责包装或阅读长篇旁白才能理解，先调整命名、分支和结构，再补缺失的就近说明，不能仅凭资深开发者看得懂或测试通过放行。
- 降低维护门槛不等于删除必要的并发、安全或原子性保护，也不等于逐行翻译代码；保留真实约束，并在对应逻辑点解释其原因和边界。

## 关键术语必须可验证

本规范允许使用“简洁”“清晰”“闭环”“同步”“必要时”“验证通过”“生产可用”等术语，但禁止把术语本身当作执行要求或完成证据。出现这些词时，必须同时写出检查对象、触发条件、通过标准和不满足时的处理方式；只有形容词、没有判定条件的句子视为无效规则。

### “完整”“闭环”“生产可用”

使用这些术语时，至少逐项确认并记录：

- 真实入口已经接通，包括路由、命令、Worker、Collector、注册表或运行时加载点；只有 helper、DTO、模板、页面外壳或测试构造不算入口。
- 主调用链已经从入口追到最终数据写入、外部请求、消息投递、文件输出或响应写出；每个新增分支都有调用方，成功和失败都能形成确定结果。
- 参数校验、权限与安全、事务、幂等、超时、取消、重试、并发上限和资源释放按实际故障模型处理；不适用项必须说明为什么不适用。
- API、配置、数据库、Redis、SQL/Lua、业务码、i18n、前端、文档、测试和运维交接已逐面检查；不能用“已同步相关内容”替代清单。
- 最后一次修改后已有可复现验证。受环境阻塞的路径必须标记未验证，并说明影响、替代证据和上线前责任人，不能写成“生产可用”。

### “简洁”“清晰”“易读”“易维护”

这些词必须落实为代码结构判断：

- 每个新增目录、接口、结构体、状态、分支、wrapper 和 helper 都能指出当前需求、真实调用方、稳定复用边界或故障证据；仅为“以后可能复用/替换”而增加的层级不得保留。
- 主流程能够沿业务顺序阅读；只转发参数且不承担校验、转换、事务、重试、隔离外部依赖等职责的包装应内联，连续跳转不能掩盖真实副作用。
- 相同业务规则只保留一个权威实现；重复判断、魔法字符串、catch-all `Manager/Helper/Common`、职责与名称不符的对象必须合并、重命名或删除。
- 锁、租约、幂等、CAS、事务、超时、取消和状态机如果保护真实并发或故障窗口，属于正确性边界，不能为了减少代码行数删除。
- 清理现有代码或文件时必须先分类：能从真实入口到达最终副作用的是“生产已启用”；没有当前业务调用方、但仍承载稳定扩展契约、已有多实现、外部依赖隔离、跨服务共享约定、CLI/Make/测试/部署/运维入口或明确职责与聚焦测试的是“基础能力但当前未启用”；只有所有入口与独立职责均消失、已有权威替代且删除不损失当前能力边界的才是“确认废弃无用”。不得仅凭 `rg` 没搜到业务调用方删除基础能力。
- 注释说明代码无法自行表达的业务意图、数据来源、单位、边界或风险；重复函数名、逐行翻译代码和“处理数据”“优化逻辑”不算有效注释。

### “小而聚焦”“当前基线”“不改变语义”

- 每个修改文件和关键 diff 都必须能映射到已确认需求、必要同步面或验证修复；无映射的重命名、格式化、目录调整和顺手重构应移出本任务。
- 当前基线必须明确请求字段、响应字段、业务码、安全策略、配置键、数据库/Redis 数据形状、错误、时序和副作用；不能只比较函数签名。
- 不保留旧字段/配置别名、旧协议分支、双写双读或历史 fallback。确定当前唯一契约后，同批更新全部仓库内调用方、测试、样例、文档和初始化资产并删除旧路径；不得引入兼容窗口或迁移分支。
- 普通重构不得改变当前基线的外部行为；需求明确调整契约时，直接更新唯一基线并记录新行为、内部调用方和验证结果。

### “同步”“相关”“按需”“必要时”

- “同步”先以源码 diff 和调用方搜索识别触发面。route、request/response、RouteMeta、安全字段、业务码、i18n、前端 wrapper/type、配置样例、Model、初始化 DDL/DML、Redis Key、SQL/Lua、测试、文档和运维步骤是发现清单，不是要求每项都产生文件的固定表单；每个触发面必须记录源码依据、修改文件和验证结果。只有常见风险面容易被误判为已处理时才写不适用及具体依据，禁止用一个汇总“不适用”覆盖未检查项。
- “相关文件”“相关测试”“按需处理”不能单独作为指令；必须给出发现方式或触发条件，例如“修改共享查询 helper 时运行所有调用包测试”“改变可见交互时补浏览器冒烟”。
- “必要时”后必须紧跟可判断条件、执行动作和证据。无法写出触发条件时，应删除该词并明确选择，或在实现前向开发确认。

### “高性能”“安全”“风险可控”

- 性能结论必须绑定热路径、调用频率、数据规模、索引/执行计划、扫描行数、返回行数、I/O 次数、batch、timeout、concurrency 和压测或基准证据；没有前后数据时只能说明完成了风险控制，不能宣称“性能已优化”。
- 安全结论必须列出身份来源、鉴权、权限、输入边界、敏感字段、密钥/随机数来源、重放防护、日志脱敏和失败业务码；通过正常请求测试不能证明安全路径完整。
- 风险说明必须包含触发条件、影响对象、监控指标、停止条件、恢复或补偿动作和责任边界；“风险较低”“可控”不能作为上线依据。

### “Bug”“阻塞”“异常”必须按触发条件分类

每个问题只记录在下列一个主分类中；严重程度与触发概率另行评估，不得因“极端”就降低影响等级：

- **正常逻辑缺陷**：在 MySQL/Redis/MQ 等依赖健康、配置符合文档、输入属于普通业务值或可预期非法值、并发处于已声明范围时，代码仍返回错误结果、改写错误状态或违反契约。例如比较逻辑把 `1 > 2` 判定为 `true`、有效请求走错分支、普通重复请求破坏幂等。这类问题必须修正代码并补稳定回归测试，不得用“数据少见”或“不容易触发”降级为环境问题。
- **极端运行条件**：Redis、MySQL、MQ、DNS、网络或磁盘整体不可用/不可达，连接持续超时、网络分区或进程资源耗尽。先记录外部触发条件，再标记“代码处理符合预期”或“存在韧性缺陷”：代码在明确超时内返回受控错误、不误写数据并释放连接、锁和 goroutine 时，依赖失效本身不记为代码 bug；代码出现无界阻塞/重试、误写/误删数据、资源泄漏、伪成功或终止进程时，记为“极端条件触发的代码缺陷”，并修正超时、降级、资源释放、就绪状态和错误传播。
- **验证环境阻塞**：验证目标本来要求 Redis、MySQL 等依赖健康，但本机/测试环境缺少依赖、Docker、`promtool` 或网络权限，命令在到达待测业务或错误处理逻辑前失败。这类项目只能证明候选版本存在未覆盖路径，不能单独证明生产代码有 bug，也不能写成验证通过；必须列出原命令、第一处环境错误、未覆盖范围和 CI/上线前补跑责任。若测试主动注入依赖不可达并已执行到待测错误处理代码，则归入“极端运行条件”，不能因同样出现 `connection refused` 改记为环境阻塞。

分析和交付输出必须按“正常逻辑缺陷”“极端运行条件”“验证环境阻塞”三栏列出项目；极端运行条件栏必须同时给出代码处理状态。每项写明触发条件、源码/日志/测试证据、期望行为、实际行为、影响范围、代码责任和处理结论。禁止把依赖不可达、代码判断错误和本机工具缺失混在一个“问题/阻塞”列表中或合并统计。

### “验证通过”“已完成”

- 验证记录必须包含最后一次修改后的完整命令、执行目录、范围、退出结果和未覆盖路径；旧快照、只测 helper、只看编译或只运行 happy path 不能证明整项需求完成。
- 文档改动至少检查相对链接、导航、Admin 代理权限、命令和路径；Skill 改动还要检查 frontmatter、触发描述、引用资源和两个仓库的一致性。
- 最终交付必须把状态明确分成已完成且已验证、已完成但未验证、已跳过、被阻塞、交付待人工执行，禁止只写“已完成”“测试正常”或“问题已解决”。

编写新规则时优先使用“当 `<可观察触发条件>` 成立，检查 `<明确对象>`，执行 `<具体动作>`，以 `<命令/状态/输出>` 为通过证据；禁止 `<可识别的错误做法>`”的句式。README 可以保留导航摘要，Skill 的执行步骤、AI 开发规范和验收清单不得用摘要替代上述判定细节。

## 1. 总原则

- 先读现有代码和文档，再改代码；不能只凭通用经验生成实现。
- 所有非平凡任务必须按标准开发执行流程推进：意图确认、源码证据、边界说明、实现、同步面检查、验证、交付复核。
- 需求或问题表述不充分、存在多种解释、目标仓库/入口不清或涉及接口、数据、权限、安全、大表、缓存、迁移时，必须先结合代码和文档说明理解、证据、待确认点和执行边界；未经确认不得直接落代码。
- 优先延续当前项目模式和现有分层；遇到成熟通用能力、高风险基础设施或手写实现容易出错的场景，必须先检查现有实现和成熟依赖/框架。确需新增抽象、目录、框架或依赖时，先说明必要性、收益、替代方案、影响范围和验证方式，并让开发确认后再落地。
- 每个新增目录、接口、结构体、状态、分支、wrapper 和 helper 必须满足本页“简洁/清晰/易维护”的判定清单；没有当前需求、真实调用方、稳定复用边界或故障证据的抽象不得保留，只转发参数且无独立职责的包装应内联。
- 性能改动先记录请求热路径、调用频率、数据规模、DB/Redis 往返、扫描/返回上限、分配、batch、timeout 和 concurrency；没有执行计划、trace、基准或前后指标时，只能说明减少的具体 I/O/扫描/分配，不能宣称性能已提升。
- 每个 helper、interface、wrapper、状态和分支都必须解决当前已证明的问题。旧字段/配置别名、旧协议和历史双轨逻辑直接从当前基线删除；鉴权、迁移互斥、资源释放、依赖故障处理及部署模式等当前正确性边界保持最小且可测试。
- 代码、配置和文档说明至少提供一项代码本身无法表达的信息：业务原因、数据来源、单位、空值、上限、顺序、并发、失败策略、部署边界或运维风险；逐字复述标识符、“处理数据/优化逻辑/异常兜底”和与实现不一致的说明均不合格。
- 重构必须保证原有能力不遗漏，并说明迁移后的入口、影响范围和验证方式。
- 需求任务及其拆解出的每个小任务必须按真实入口、调用链和交付面闭环完成；禁止只搭骨架、只写样例、只实现基础能力、单一分支或 happy path 后宣称完成。
- 文档、接口、测试和配置必须与代码同步；发现旧文档与代码不一致时要一并修正。
- 配置热加载必须区分运行参数和启动期注册开关；路由、handler、插件、基础设施连接等启动期能力不在线补注册或重建，变更后必须通过 `restartRequired/restartReason` 暴露重启原因。

## 2. 命名要求

- 命名必须短而准确，贴合当前领域语境；禁止随意取名、过度缩写或堆很长的描述性名字。
- 目录、变量、方法、常量、结构体、接口和字段命名必须与当前职责一致；实现职责变化后必须同步改名，禁止沿用旧名、泛名、错名或过长说明式命名。
- Go 包名短小、全小写，不使用下划线。
- 方法名使用“动词 + 对象/结果”表达行为，例如 `BuildPayload`、`SyncPeriodicTasks`；私有 helper 只覆盖当前意图，避免 `handleData`、`doProcess` 这类泛名。
- 变量名按作用域控制长度：短作用域可用 `ctx`、`err`、`tx`、`db`、`uid`、`rows`；跨多段逻辑的变量必须写清领域含义。
- 结构体使用名词或领域对象命名；请求以 `Req` 结尾，响应以 `Resp` 结尾，列表项以 `Item` 结尾。
- 接口按能力命名，优先使用 `Reader`、`Writer`、`Repository`、`Provider` 等自然后缀；只有一个实现且无替换点时不要强行抽接口。
- 新增抽象前必须确认真实替换点、稳定复用边界和维护成本；新增接口、目录、wrapper 或 helper 必须满足至少一项：隔离外部依赖、解除真实依赖环、承载两个及以上现有实现、收口两个及以上调用方已稳定的同一业务规则，或删除主调用链中的重复状态转换。仅以“未来可能复用或替换”为理由不得抽象。
- 常量按领域前缀集中定义，名称表达稳定业务含义或枚举语义；禁止魔法字符串、随意数字和含糊的 `DefaultValue`。
- 切片、map 命名体现内容和单位，例如 `userIDs`、`queueWeights`、`workflowByName`。
- 路由别名使用 `domain.resource.action`，例如 `task.workflow.trigger`。
- Redis Key 必须集中在 `common/rediskeys`，禁止业务代码临时拼接高基数通配 Key。
- 工作流和批处理链路统一使用 `workflowID`、`mode`、`node`、`shardIndex`、`shardTotal`、`uid` 等命名。

## 3. 注释要求

新增或重构的变量、常量、方法、结构体及字段、map 字段含义、路由、GORM Model、接口和关键逻辑按下述要求补中文注释，说明职责、数据来源、单位、空值或约束；注释是代码易读、易维护的实现要求，不是交付后的装饰。

顶层稳定契约中的 map、数组、切片等字段，必须说明元素 key/value 或元素对象含义、数据来源、边界条件、排序/去重和空值语义。

注释必须说明业务意图、数据来源、边界条件、性能保护点或降级策略。禁止重复代码本身，也禁止只写“优化”“兜底”“处理数据”这类含糊描述。一句话能说明白的不要写成长段。

- 方法注释说明业务职责、前置条件和调用边界，不罗列内部步骤；方法头不能代替各逻辑点的就近说明。
- 方法内部的查询准备、条件分支、状态变更、写入、重试和资源释放，凡有业务原因、先后顺序、并发约束或失败策略，都在对应步骤或分支前说明；涉及多阶段 I/O 时写清前置结果和已发生的副作用。
- 事务、锁、租约、CAS、幂等、重试、降级、批处理、状态迁移、安全校验顺序和资源清理必须在对应逻辑块前说明其保护的并发、数据或安全边界；方法头注释不能替代块内说明。
- 一个逻辑点，一条就近说明；三个独立逻辑分别写三条，不在方法开头或单处笼统概括，一句话能说清楚就不写成长段。
- 复杂条件如果无法通过准确命名直接表达，注释说明业务判定和边界值；普通赋值、显然的空值判断及统一错误包装不写逐行注释。
- 初级开发者应能通过主流程、就近注释和测试理解需求规则、前置条件、关键副作用及失败终态，并找到修改与回归位置；长篇说明仍解释不清时，先简化分支、命名或无职责调用。

### YAML 配置字段行级注释

项目自有的应用配置 YAML 是对开发、测试和运维公开的配置契约，不能只给父节点写一条概述。新增或修改配置结构、默认值、校验、加载来源或生效方式时，按以下规则维护 `etc/config*.sample.yaml`、外置运行期配置样例和项目自有部署配置模板：

- 每个由项目代码读取的固定字段必须在字段正上方放置中文 `#` 注释，注释缩进必须与字段一致；父 mapping、父 list 或章节标题的说明不能代替固定子字段的行级注释，行尾注释也不能作为唯一说明。
- 每条字段注释先写消费组件和用途，再用简短语句说明源码已定义的类型/数据形状、枚举、范围、单位、缺省/空值/零值、normalize/getter 回退、热加载或重启、敏感信息来源和跨字段约束；不能为追求短句省略真实边界，也不得猜测源码未定义的行为。
- mapping 或 list 父字段必须说明子项数据形状、唯一键或顺序是否有意义、空对象/空列表行为以及覆盖或合并规则。固定结构的每个子字段仍需单独注释；动态 map 的业务 key、地址映射或重复列表项，只在父字段已经明确 key/value 语义、约束和空值行为时，允许不为每条数据复制同一句注释。
- 密钥、密码、token、私钥、完整 DSN 等敏感字段只说明注入来源、是否允许为空、最小约束、轮换或重启边界；注释、样例、日志和交付记录均不得包含真实值。样例使用可识别占位值，本地实际配置从带注释样例复制，并在新增字段时保留对应说明。
- `docker-compose*.yml`、CI workflow、Prometheus rule 等由外部工具定义的 schema，纯数据清单以及生成文件不机械套用应用配置规则。排除时必须记录文件路径、schema 所有者、文件职责和项目代码不把其字段作为应用配置读取的依据；其中项目自定义的环境变量或嵌套应用配置仍需在所属模板处说明。
- 修改注释前先核对 config struct/tag、默认值、normalize/getter、校验器、实际消费方和 reload 应用器。无法从源码证明默认值或生效边界时，先补证据或向开发确认，禁止编造“默认即可”“支持热加载”“修改后重启”等结论。

通过标准：所有纳入范围的固定字段都有紧邻且同缩进的有效中文注释；YAML 解析和配置样例加载测试成功；字段名、默认值和 reload/restart 说明与最后一次修改后的源码一致；排除文件具有逐文件依据。只写“配置字段均有说明”或只检查 YAML 能解析，不算完成。

## 4. 数据库与缓存规范

- MySQL/SQL 优先使用 GORM 链式调用；允许复制延迟的查询使用 `ReadDB`，写入、写后读、鉴权撤销和一致性回源使用 `WriteDB`；事务内始终沿用同一个 `tx`，不能根据语句是查询就切换到读副本。
- GORM 沿用 `SkipDefaultTransaction: true`；仅在多条 SQL 必须共同提交或读取必须保持同一快照时使用显式事务，单条原子 SQL 不额外包事务；一次 GORM 调用可能跨批或执行 Hook，必须按实际 SQL 判断。
- 开启事务前完成参数解析、格式校验、哈希计算、数据整理及不依赖事务快照的查询；事务内只保留原子读写、锁定读取和提交条件重验，不能为缩短事务制造检查与写入竞态。
- 事务内禁止 HTTP/RPC、Redis/MQ、文件处理、等待及退避重试等非数据库工作；这些步骤按业务依赖前置或后置，提交后副作用失败沿用既有重试或补偿路径，不能误报未提交或直接重放整笔写入。
- 每个事务必须明确扫描/写入行数、批量、执行时间和锁等待上限，结合索引、并发及连接池预算验证；禁止用无界循环、大范围扫描或耗时计算延长持锁时间，也不能仅把大事务移到后台就视为解决。
- 只有业务允许独立提交时才拆成有界小批；必须整体原子提交但超出资源预算时，先限制单次规模或调整并确认方案，不得静默分批破坏原子性。改动事务边界须验证最坏批量、并发竞争、超时/取消和部分写入失败后的最终状态。
- 只有 GORM 无法安全表达、动态 DDL/批量切表/ClickHouse 聚合等链式调用不适用，或链式调用会严重影响性能时才允许原生 SQL；使用前必须写清必要性、索引依据、预估扫描范围、分页/批量上限、超时/并发控制和 DB 压力。
- 所有新增或调整的 SQL 都必须先评估执行计划、索引、基数、返回行数和目标库压力；禁止用历史遗留 SQL 风格代替性能评估。
- 需要随应用或已产品化运维工具运行的原生 SQL 必须保存为稳定 `*.sql.tmpl` 资产并由真实调用方加载；禁止在 Go 业务代码中内联多行 SQL、`fmt.Sprintf("SELECT ...")` 或模板外 `Exec("RENAME TABLE ...")`。一次性 DBA 变更 SQL 不属于代码资产，按下述仓库外流程交付。
- `.lua` 是 `go:embed` 加载的 Redis Lua 脚本代码资产，必须提交仓库；禁止在 Go 业务代码中使用 `redis.NewScript(...)` 内联 Lua。
- 仓库内 DDL、DML 和 `defaultMigrationSpecs` 维护完整初始化基线，不承担日常逐版本升级。新库可一次初始化；非空库可在授权后执行未登记的幂等资产并重试未完成资产，已登记且匹配的项跳过；不能因库非空而拒绝执行，也不能将重跑解释为强制重写已登记资产。
- 禁止新增按需求、日期、工单或版本拆分的 `add_*`、`alter_*`、`sync_*`、`*_seed_*`、`*_repair_*`、`*_backfill_*` 等碎片化迁移 SQL，也不得向 `defaultMigrationSpecs` 追加日常变更版本。
- 存量库增量 DDL/DML、回填、修复和补偿 SQL 只生成到被忽略的 `data/sql-changes/<change-id>/`，通过发布工单或受控渠道交给 DBA/运维命令行执行；不提交、不暂存、不登记到项目迁移表。
- DBA 交付必须说明目标环境/实例/库/表、当前与目标版本、SQL SHA-256、执行顺序、索引和扫描边界、锁表风险、批量/超时/并发、备份、验证、停止条件及恢复方案。只给 SQL 文本不算完整交付。
- 本仓使用 `api_schema_migrations` 登记初始化资产，两仓在同库使用独立登记表并共用迁移锁；迁移命令严格校验本仓版本、名称、资产和 checksum，不能伪造或删除记录绕过差异。DBA 人工变更造成的登记差异不参与服务启动门禁，但不能据此忽略真实表结构、权限或连接错误。
- SQL seed 如果显式保留自增主键 `id`，新增行必须按 `id` 递增放在对应位置，不能为了贴近同类业务行插入到中间。
- 新增或移动 `*.sql.tmpl`、`.lua` 时，必须同步检查 Go 侧 `//go:embed`、渲染方法和最小单测。
- Go 调用侧必须使用 `embedasset.StripLeadingLineComments(template, "--")` 或当前包 helper 剥离文件头说明，再交给 MySQL、ClickHouse 或 Redis 执行。
- 不允许在业务接口中执行 Redis 全库 `SCAN` 或模板通配扫描；高基数缓存必须通过索引集合、精确 Key、白名单模板、登记模板或异步离线任务处理。
- API 已维护 `SysConfigLogic`、`SysConfigKey`、table-cache 目标和 Redis Key 作为共享运行期配置基础能力，但当前业务 route/logic 尚未调用，状态为“基础能力/未激活”。新增读取需求时必须复用现有能力，并补真实调用方、缺失/非法值行为、缓存一致性、故障降级和调用链测试；在这些证据完成前不得把该能力描述为生产已启用，也不得另建重复 getter、注册表或缓存框架。
- 重构时优先复用现有 helper、模板渲染器、分页游标、去重和错误包装方法；同类逻辑重复时抽到当前包公共 helper。

`*.sql.tmpl` 文件头使用连续 SQL 行注释，只记录用途、方言、调用方、参数来源和安全边界；同一信息不得在多行重复：

```sql
-- 代码资产：说明该 SQL 模板解决什么问题。
-- SQL 方言：MySQL / ClickHouse / ANSI SQL；使用窗口函数、JSON、在线 DDL 或版本相关语法时写明最低版本和方言限制。
-- 调用方：说明 Go 侧函数或方法名，以及 go:embed 加载后会先剥离本说明再执行。
-- 参数来源：说明占位符、绑定参数、动态表名或条件片段来自哪里。
-- 安全边界：说明白名单、转义、参数绑定、批量上限、事务或幂等边界。
```

`.lua` 文件头使用连续 Lua 行注释；涉及删除、释放锁、续租等敏感操作必须写清 owner 比对或防误删策略：

```lua
-- 代码资产：说明该 Redis Lua 脚本解决什么问题。
-- 调用方：说明 Go 侧函数或方法名，以及 go:embed 加载后会先剥离本说明再发送 Redis。
-- KEYS[1]：说明 Redis Key 来源、所属 Redis Key 模板和是否高基数。
-- ARGV[1]：说明参数来源、类型和边界。
-- 原子性边界：说明脚本内原子操作范围、owner 校验、TTL 或幂等策略。
```

## 5. 错误处理规范

- 请求、消息、任务、配置热更新、外部依赖、重复注册、超时或取消能够触发的失败属于运行期可恢复错误，必须返回 `error`、业务码或受控任务失败，由 handler、worker、scheduler、health 或 startup 最外层记录；禁止在服务运行路径使用 `panic`、会 panic 的 `Must*`、`log.Fatal*`、logger `Panic*`、`os.Exit`、`syscall.Exit` 或 `runtime.Goexit`，也禁止依赖 Recover 掩盖可预期错误。路由、组件和指标等启动注册必须在 `App.Start` 前完成并逐层返回错误，注册失败时拒绝启动并执行已创建资源的清理；只有 `cmd/*` 主入口可以在服务尚未监听，或全部监听器和后台组件已经停止且资源清理完成后，把最终进程结果转换为退出码，失败结果必须非零。只有包初始化读取编译期固定常量或 `go:embed` 资产、触发条件不受任何运行期输入影响且存在完整性测试时，才允许用 `panic` 表示二进制构建资产已损坏；注释必须写明初始化阶段和不可恢复依据。
- 底层错误必须使用 `github.com/Is999/go-utils/errors` 的 `errors.Tag`、`errors.Wrap` 或 `errors.Wrapf` 包装。
- 同一个函数里，同一个 `error` 值只包装一次；跨函数边界可以继续包装，因为那是新的调用语义和上下文，避免裸错误漏出去。
- 业务中间层只返回错误，不打印 `error` 级日志；禁止在 logic、repository、service、model、helper 等内层随意调用 `loggerx.Errorw`、`loggerx.ErrorTextw` 或 `logx.Error*`。
- 顶层 handler、启动入口、健康检查或不可返回错误的兜底协程统一打印 `error` 级日志；同一错误链路只能在最外层打印一次。
- 底层需要补排障信息时只能通过 `errors.Wrapf` 写入上下文字段，不能用多处 `error` 日志替代错误链。
- 错误上下文必须带可追踪字段，例如 `workflow_id`、`mode`、`node`、`shard`、`uid`、`task_id`、`event_id`。

```go
if err != nil {
    return errors.Wrapf(err, "工作流节点执行失败 workflow_id=%s mode=%s node=%s shard=%d/%d", workflowID, mode, node, shardIndex, shardTotal)
}
```

## 6. 日志规范

- 日志统一使用 `loggerx.Infow`、`loggerx.Debugw`、`loggerx.Errorw`。
- 正常流程只打印关键节点，不刷屏。
- `error` 级日志只在最外层打印一次；底层通过错误返回和错误包装保留上下文。
- 顶层结构化字段只保留公共检索维度，例如 `trace_id`、`route`、`user_id`、`http_status`、`biz_code`、`error`、`error_chain`、`task_id`、`workflow_id`、`mode`、`node`、`shard`；其它细节交给 `loggerx` 写入 `content`。
- 日志字段类型必须稳定；时间窗口和间隔细节使用带单位的字段名，例如 `window_start_unix`、`interval_seconds`。

```go
loggerx.Infow(ctx, "工作流节点开始处理",
    logx.Field("workflow_id", workflowID),
    logx.Field("mode", mode),
    logx.Field("node", node),
    logx.Field("shard", shardIndex),
)
```

## 7. 接口与业务码规范

- 普通 JSON API 响应使用统一结构 `status/code/message/data/traceId/spanId`；下载、Range、SSE 等按各自协议返回，不强行包装成 JSON 或整包缓冲。HTTP 状态与业务成功标志分别按业务码契约判定。
- 客户端需要采取不同处理的业务分支使用可区分业务码；账号枚举、验签/解密阶段探测等安全场景保留统一对外错误，真实原因只写入脱敏日志或审计。响应 `message` 不暴露 SQL、密钥、内部表名或下游原始错误。
- 新增业务码必须补中文和英文文案。
- 新增接口必须补接口文档，文档格式遵循 [接口文档统一规范](接口文档/接口文档统一规范.md)。
- 新增路由必须在模块 `RouteSpecs` 中声明 `RouteMeta`、接口文档、安全链路和中文说明；需要登录态的路由必须走 `AuthMiddleware`。
- 内置和扩展路由的 `RouteMeta.Access` 与 `RouteSpec.Chain` 都必须使用固定映射：`public` 只能对应 `none` 或 `public`，`auth` 只能对应 `auth`，`internal` 只能对应 `internal`；注册器遇到缺失、未知类型或不匹配组合必须返回带 module、method/path 和监听器边界的启动错误，由 bootstrap 拒绝启动，禁止 `panic` 或继续注册。
- 路由别名被 `RouteMeta`、`RouteSecurityPolicies`、鉴权事件、测试或文档防漂移逻辑复用时，必须先收口到 `internal/routealias` 常量，禁止多处重复写字符串。
- 公开路由必须写清公开原因和 token 校验边界，例如登录、注册、健康检查和指标抓取。
- 内网运维路由必须使用 `/internal/` 前缀和 `internal` 安全链路，只能注册到独立 `internal_server`；必须校验 Ops HMAC 与 Redis nonce 防重放，生产跨主机链路使用 mTLS。
- 请求和响应签名只能在 `RouteSecurityPolicy` 中显式列出关键字段，禁止默认使用 `*` 对完整请求体、完整响应 `data`、大结构体或分页列表整体签名。
- `RequestSign/ResponseSign=nil` 表示关闭签名；显式空切片表示只签 `appID`、`traceID`、`timestamp`，不得把空切片误判为关闭。
- 请求和响应加密只能使用字段级路径，请求字段必须由 `RouteSecurityPolicy.RequestCipher` 声明，禁止默认使用 `cipher` 整包加密；仅对 token、金额、订单号、手机号、邮箱、二次校验字段等重要字段做轻量加密。
- `sign_status=1, crypto_status=0` 允许单独签名；`crypto_status=1` 时 `sign_status` 必须为 `1`。组合模式下每个 `RequestCipher/ResponseCipher` 点路径同时出现在对应签名字段，请求先验签密文再解密，响应先加密再回签。
- 单个接口参与签名或加密的字段最多 8 个；普通安全字段最大 4KB，`json:` 小对象最大 8KB，禁止用安全链路承载大对象、大数组或分页列表。
- 安全中间件读取请求体最多 64KB；超过该上限的业务数据不得依赖签名/加密中间件解析，必须拆成受控字段或走专用上传/异步流程。
- 请求验签、密文格式和解密失败必须对外使用同一业务码与文案，具体阶段只写入脱敏日志、trace 和风控事件；AppID、密钥可用性、响应签名/加密和字段超限继续使用独立业务码。
- 接口文档必须用 `### 安全字段` 表写清参与签名和加密的具体字段；没有业务签名字段但启用基础头签名时必须明确写出，不能标记为不参与签名。
- 修改登录、刷新、退出或鉴权逻辑时，必须同步校验 HS256、issuer、稳定 `sid`、唯一 `jti`、`auth_version`、AppID、同槽 Redis Lua 原子创建/校验/轮换/失效、认证版本键有界 TTL、刷新完整旧 token CAS、刷新与退出并发收口、每用户会话上限、主库用户状态与认证版本、后台已提交版本同步和 `auth.security` 脱敏事件边界，并补生命周期与并发测试。
- 接口文档如果发现与代码不一致，必须同步修正，不能继续保留误导性描述。

## 8. 大数据查询与批处理规范

- 涉及大表、大结果集或高频查询时，必须先评估数据量、索引、执行计划、并发量和目标库压力，不能直接上线试跑。
- 在线接口禁止无上限全表查询、深分页 `OFFSET`、`SELECT *`、无索引排序/聚合/JOIN、一次性加载超大 ID 集合。
- 查询必须有明确边界，优先按时间窗口、主键游标、分片或状态分页推进；`batch_size`、最大批次数、超时、并发和 `sleep/backoff` 必须可控。
- 大聚合、历史回补、跨库对账、批量修复和导出应走受控异步任务、维护队列、汇总表、ClickHouse 或数仓，禁止放在 HTTP 请求内长时间执行。
- 业务允许独立提交的批量写入和删除按主键或索引分成有界小批，支持幂等、断点和中止；需要整体原子提交的操作按事务预算限制规模，不得以缩短事务为由拆坏数据一致性。
- 只读且允许复制延迟的查询使用读库；跨期聚合、分析和对账使用 ClickHouse/数仓或离线链路；预估扫描/返回规模超过在线上限、执行时间超过请求 timeout 或并发可能耗尽连接池时，必须转队列/后台任务并设置限流、熔断或降级，不能继续放在 HTTP 热路径。
- 新增大数据查询必须补充索引依据、保护阈值、关键日志/指标和最小测试；无法验证执行计划时，要说明风险和上线观察方式。
- 前台列表接口不默认实时统计超大总数；确需统计时使用缓存、异步汇总或受控近似值，并在接口文档说明口径。

## 9. 前端联动规范

- 接口字段以当前唯一契约为准；禁止保留 snake_case/camelCase 双字段解析、旧字段别名或宽松兼容。字段调整时同批更新后端调用方、Admin 代理、文档、样例和测试。
- 敏感操作必须复用既有登录态、签名、加密、秘钥版本或二次校验机制。
- 加密、签名、秘钥版本配置变更后，必须同步更新启动校验、接口文档、配置样例和前端配置说明。
- 前端请求不得默认把整份表单、筛选条件或大 JSON 对象纳入签名/加密；只传后端文档声明的关键字段。
- RSA 私钥生成和下载只允许由客户端本地完成，禁止新增后端生成私钥、下载私钥或返回私钥明文的接口。
- 前端展示错误优先使用后端业务码和国际化消息，不硬编码后端内部错误。

## 10. 文档质量

- 先明确受众和任务：README 面向首次接手者，开发规范面向实现与评审，接口文档面向调用方，运维手册面向发布和排障。
- 标题表达稳定主题或结论，步骤按真实执行顺序排列；文档超过两个二级章节时在侧边栏或正文目录提供可点击入口，同一规则正文只维护一份，其它入口写摘要并链接权威正文。
- 命令、路径、配置键、默认值、接口字段和示例必须能从当前仓库验证；共享内容先与 `admin-go` 并排核对，不能机械复制项目名称、路由或部署边界。
- 文档只描述当前代码和部署资产已支持的行为。计划、假设和未完成项必须明确标注，不能写成已上线能力。
- 不保留“最近一次测试通过”“当前没有问题”等会自然失效且缺少候选快照的状态性结论；验证结果写入具体交付记录。
- API 文档资源只通过内网 `/internal/docs` 提供给 Admin 代理，不得描述为浏览器可直接访问的公开文档站。
- 修改 Markdown 时检查相对链接、侧边导航、Admin 侧文档权限资源和代理访问边界；同一规则只保留一个权威正文，其它入口使用摘要和链接。

## 11. 质量门槛

Go 实现变化优先运行全量测试；纯文档、Skill 或 agent 元数据变化只运行相应格式、引用、脚本自测和规则语义检查，不把业务全量测试作为文案修改的固定门槛：

```bash
go test ./...
```

Go 改动范围较小或全量测试受阻时，至少执行归属包和直接调用包测试，并说明未覆盖范围与原因；并发和外部依赖行为变化分别补 Race、隔离集成或冒烟验证。

提交前必须自查：

- 是否误删功能。
- 是否在需求或问题不清时先基于代码和文档确认意图、证据、待确认点和执行边界，而不是直接猜测实现。
- 是否逐项完成需求任务和拆解后的小任务，并明确说明完成状态。
- 是否存在只实现基础能力、只打样、未接入真实调用链或未验证却宣称完成的半成品。
- 是否复查目录、变量、方法、常量、结构体、接口和字段命名，确保短而准确且贴合当前职责。
- 是否先评估成熟依赖/现有实现；新增抽象、目录、框架或依赖是否已有开发确认。
- 是否存在未使用代码、重复抽象、过度封装，或因拒绝成熟依赖而手搓高风险基础能力。
- 初级开发者能否通过主流程、就近说明与测试理解需求规则、定位修改及回归；能否逐项指出事务必要性、前置工作、原子性与资源上限，不能只凭功能测试通过放行。
- 是否优先使用 GORM 链式调用；原生 SQL 是否具备必要性说明和性能保护边界。
- 是否只更新完整初始化 DDL/DML，且没有新增碎片化迁移 SQL 或向 `defaultMigrationSpecs` 追加日常版本。
- 存量库本地 SQL 是否位于被忽略的 `data/sql-changes/<change-id>/`、未进入 Git，并具备 DBA/运维执行与恢复说明。
- 是否使用 `errors.Tag` 或 `errors.Wrapf`。
- 是否把 `error` 级日志留在 handler、启动入口、健康检查等最外层。
- 是否让 `*.sql.tmpl`、`.lua` 文件头说明在执行前通过 `embedasset` 或当前包 helper 剥离。
- 新增或重构的变量、常量、方法、结构体/字段、map 字段、路由、GORM Model、接口和关键逻辑是否有中文注释，且注释是否给出业务原因、数据来源/单位、边界或风险，而非复述代码。
- 是否补接口文档、开发文档和必要测试。
