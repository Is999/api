# API 开发扩展指南

本文说明如何在 `api-go` 新增或修改前台业务能力，并把路由、安全、业务码、数据、缓存、配置、文档、测试和发布闭环到同一候选版本。它面向已经了解 Go 和 go-zero 的后端开发人员；强制命名、注释与质量规则以[AI 开发规范](角色文档/后端开发/AI开发规范.md)为准，注册入口以[组件注册清单](角色文档/后端开发/组件注册清单.md)为准。

## 1. 服务边界

API 是前台请求热路径，新增能力应满足低延迟、有界依赖和失败可解释：

- 用户注册、认证、资料、session 和受控运行期配置属于 API。
- 管理员后台、运营任务、Asynq、Scheduler、离线批处理和大规模数据修复属于 `admin-go`。
- 请求链路可以投递轻量 Kafka 事件，但不能同步执行长任务或无边界扫描。
- 内网运维能力必须注册到独立 `internal_server`，不能因为“只有内部会调用”而挂到公网 listener。

不确定职责时，先画出调用方、数据所有者、延迟预算、失败补偿和部署边界，再决定落在 API 还是 Admin。

## 2. 标准调用链

```text
RouteSpecs
  -> middleware/security chain
  -> handler: parse + Validate + response
  -> logic: use case + transaction + cache policy
  -> model/cache/infra: database, Redis, Collector
  -> helper.JSONResp
```

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| `handler` | 路由装配、请求解析、调用 logic、写统一响应 | 业务规则、临时连接、复杂事务 |
| `types` | JSON 契约、校验、归一化、字段注释 | 数据库查询和副作用 |
| `logic` | 用例编排、授权后的业务规则、事务、缓存一致性 | HTTP 细节和路由注册 |
| `model` | GORM Model、表名、索引查询和数据访问 | 跨领域流程编排 |
| `infra` | MySQL、Redis、Collector、日志和外部依赖适配 | 业务状态机 |
| `svc` | 长生命周期依赖聚合 | 按请求创建依赖 |

新增代码优先延续现有领域目录；只有职责和复用边界明确时才新建 package、接口或通用抽象。

## 3. 新增 HTTP 能力

### 3.1 先定义契约

实现前明确：

- method、path、稳定 route alias 和访问边界。
- 请求字段、单位、默认值、上限、空值、排序和去重语义。
- 成功响应、失败业务码、HTTP 状态和中英文文案。
- 是否需要 JWT/session、请求/响应签名、字段级加密和防重放。
- 数据读写、事务、缓存、幂等和外部事件。
- 接口 QPS、延迟预算、单次查询范围和超时。

先更新或创建对应接口文档草案，有助于在写 handler 前发现字段和安全边界缺口。

### 3.2 文件落点

| 改动 | 典型文件 |
| --- | --- |
| 稳定别名 | `internal/routealias` |
| RouteMeta | `internal/handler/shared/route_meta.go` |
| 模块路由 | `internal/handler/{domain}/routes.go` |
| 模块装配 | `internal/handler/routes.go:builtinRouteModuleSpecs` |
| 字段安全策略 | `internal/security/route_policy.go` 或当前 `RouteSecurityPolicies` 入口 |
| 请求/响应 | `internal/types/{domain}.go` |
| Handler | `internal/handler/{domain}` |
| Logic | `internal/logic/{domain}` |
| Model/Repository | `internal/model` 或领域现有数据层 |
| 业务码 | `common/codes/resp_code.go`、`common/codes/contract.go` |
| i18n | `common/i18n/locales/active.zh-CN.json`、`active.en-US.json` |
| 接口文档 | `docs/site/接口文档` |
| 安全快照 | `docs/site/route_security_manifest.json` |

### 3.3 RouteSpecs

在模块 `routes.go` 中单处声明 method、path、RouteMeta、文档、安全链路、访问日志降噪和 handler。新增整个模块时，再把模块规格加入 `builtinRouteModuleSpecs`。

要求：

- alias 使用稳定的 `domain.resource.action`，被多个装配面复用时先在 `internal/routealias` 定义常量。
- 业务路由使用 `public`、`auth` 或 `internal`；`none` 仅用于已登记的无安全链探针，不能依赖 path 猜测访问边界。
- 高频 live/ready/metrics 探针才设置 `SkipAccessLog`；不要在 access log 中间件建立第二套路径白名单。
- 内网路由使用 `/internal/` 前缀和 `internal` 链路，并在策略中显式声明前台签名/加密为空。
- 接口文档路径随 RouteSpecs 登记，契约测试会校验真实路由、文档和安全链路一致。

### 3.4 Types 与 Validate

请求和响应类型必须补中文字段注释。`Validate` 负责纯校验和无副作用归一化：

- trim、大小写、去重和稳定排序。
- 长度、数量、枚举、数值范围和跨字段约束。
- UID 等可能超过 JavaScript 安全整数的值用十进制字符串传输。
- 明确 `nil`、空数组、空字符串和零值语义。
- 不查询数据库、Redis 或外部服务。

前端限制不能替代服务端校验。安全、分页、批量、重试、超时和 TTL 上限必须由服务端失败关闭。

### 3.5 Handler 与 Logic

Handler 使用现有通用 action/response 封装，保持薄层；Logic 负责真实用例：

1. 基于已验证请求执行业务前置检查。
2. 决定读库、写库、事务和锁边界。
3. 调用 model/cache/infra，并为错误补充当前业务语义。
4. 完成写后缓存失效或版本推进。
5. 构造稳定响应，不暴露数据库错误、密钥或内部拓扑。

中间层只返回错误；`error` 级日志在 handler、启动入口或不可返回错误的边界记录一次。日志携带 route、trace、user/session 哈希和稳定动作，禁止记录密码、token、明文手机号/邮箱/IP。

## 4. 访问边界与安全策略

### 4.1 四类安全链

| chain | 使用场景 | 校验 |
| --- | --- | --- |
| `none` | 健康和指标 | 不执行前台签名、加密、JWT |
| `public` | 注册、登录 | 字段安全、限流和防重放；不要求登录态 |
| `auth` | 用户资料、刷新、退出 | 字段安全 + JWT + Redis session/认证版本 |
| `internal` | 配置、运行态同步、文档资源 | 私网来源 + Ops token + HMAC + timestamp + Redis nonce；生产跨主机 mTLS |

路由是否要求 JWT、是否允许公网访问都由 RouteSpecs/RouteMeta 派生，禁止在 handler 内根据 URL 或请求头自行决定。

### 4.2 字段级签名和加密

`RouteSecurityPolicies` 必须逐路由显式声明：

- `RequestSign/ResponseSign=nil`：关闭签名。
- 显式空切片：启用基础头签名，但不拼业务字段；仍使用 `appID/traceID/timestamp`。
- `RequestCipher/ResponseCipher`：仅列需要加解密的字段点路径。

约束：

- 单接口参与签名或加密的字段最多 8 个。
- 普通字段最大 4 KiB，`json:` 小对象最大 8 KiB。
- `json:` 只用于加密字段的编解码标记：`RequestCipher: ["json:payload"]` 对应 `RequestSign: ["payload"]`；响应同理使用真实路径，例如 `json:user.profile` 对应 `user.profile`。签名覆盖最终密文，JSON 解密保留数字精度且拒绝尾随值；内置路由当前未启用该扩展能力。
- 安全中间件读取请求体最多 64 KiB；大载荷应使用上传、拆分接口或异步流程。
- 禁止使用 `*`、整包 `data`、`cipher`、大数组或分页集合。
- token、金额、订单号、手机号、邮箱和二次校验字段优先保护；普通展示字段不默认进入安全链。
- 组合模式下请求先对密文验签再解密，响应先加密再对密文回签；`responseCipher` 点路径同时出现在 `responseSign`，且 `crypto_status=1` 要求 `sign_status=1`。
- `X-Signature` 只允许短码 `R` 或 `H`，`X-Crypto` 只允许 `R` 或 `A`，其它值失败关闭。

修改字段策略后同步接口文档 `### 安全字段`、`route_security_manifest.json` 和前端 route policy。修改签名串、点路径或 `X-Cipher` 编码时，还要同步 `internal/security/testdata/security_vectors.json` 与前端测试向量。

RouteMeta、manifest、前端 TypeScript 类型、字段点路径和测试向量的同步步骤见[前端安全策略同步](角色文档/后端开发/前端安全清单同步.md)。

## 5. 业务码与多语言

新增业务码按以下顺序：

1. 在 `common/codes/resp_code.go` 声明稳定常量，保持号段职责。
2. 在 `common/codes/contract.go:defaultCodeSpecs` 声明 HTTP 状态、成功标志和默认文案 key。
3. 同步 `active.zh-CN.json` 与 `active.en-US.json`。
4. 在接口文档列出触发条件和调用方处理方式。
5. 运行 `go test ./common/codes ./common/i18n`。

不能复用语义相近但处理方式不同的旧业务码，也不能把内部错误文本直接作为前端稳定契约。HTTP 状态描述协议层结果，业务码描述可编程业务结果。

## 6. 数据库、事务与表路由

### 6.1 基本规则

- 读操作使用现有读库入口，写操作使用写库；事务内所有查询继续使用同一个 `tx`。
- 优先使用 GORM 链式调用；原生 SQL 只在 GORM 无法安全表达或会明显影响性能时使用，并维护为可审查嵌入资产。
- 列表查询必须有稳定排序、页大小上限和索引；大表使用游标/窗口，不使用深分页或无边界查询。
- 事务只覆盖必须原子提交的数据库动作，不在事务内长时间调用外部 HTTP、Kafka 或 Redis。
- 统一连接工厂设置 `SkipDefaultTransaction: true`，写操作不再自动开启事务；该策略随进程启动生效，不提供 YAML 开关。
- 注册和联系方式变更仍用显式事务共同提交用户主表与身份目录；新增跨批写入也必须自行声明原子性，不能依赖 `CreateInBatches` 自动回滚。
- 写入与缓存失效之间存在失败窗口时，使用版本、短 TTL、事务 outbox 或可补偿设计，不能假设两个系统原子提交。

### 6.2 用户和身份路由

- 注册/登录先按身份类型访问 `user_identity_username`、`user_identity_email`、`user_identity_phone`、`user_identity_oauth`。
- username 保存 `identity_value`；email/phone 保存 HMAC `identity_hash`；OAuth 保持 provider 与大小写敏感 identity。
- 身份表保存 `user_id/user_shard_no`，用于保证登录身份唯一并定位用户固定逻辑桶。
- `user_shard_no=idgen.ShardNo(user_id)`；已知 ID 的查询使用 `WHERE shard_no=? AND id=?`。
- `user.route_shard_count` 是 Admin/API 共同使用的当前用户物理表数量，只允许 `1/2/4/.../1024`；身份表只保存稳定的 `user_id/user_shard_no`，不绑定物理拓扑。
- 本分支通过共享 `internal/sharding` 按固定桶选择物理表，业务代码不得自行拼接表名；`user`、`user_tag` 和其它 UID 表使用同一固定逻辑桶，但可以按容量独立配置物理分片数。
- 扩容使用 Admin 同名分支的 `cmd/tableshard` 完成嵌入式全量和 binlog 增量迁移，最终短暂停写并同步切换 Admin/API 启动配置，不增加常驻代理服务。

新增身份类型或扩容用户表必须先设计唯一性、登录路由、全量/增量回填、一致性校验、灰度切换和回滚，不能只增加 Model。

## 7. Redis 与缓存

- 所有 Key 模板集中在 `common/rediskeys`，实际 Key 通过 app scope helper 加 `app_id`。
- 精确读取、删除和版本推进使用 helper；在线请求不执行 `KEYS` 或无界 `SCAN`。
- `sys_config` 基础能力使用 `config_uuid:%s` 模板和 `app:{app_id}:...` 实际命名，与 Admin 同站点共享一致性边界；当前业务 route/logic 尚未读取，状态为“基础能力/未激活”。
- 配置 Hash 仅保存 `type`、`value`；回源额外查询 UUID 做精确校验，不缓存标题、备注或层级，刷新整 Hash 后移除多余字段。
- 缓存缺失由 redsync 锁保护回源，并使用短 TTL 空值占位防穿透。用户资料重建使用 `WithLockOnce` 单次抢锁：当前实例成功持锁时再次检查缓存后回源；锁已被其它实例持有时不重复抢锁，立即读取一次缓存，再按 `50–100/100–150/150–200/200–250/250–300ms` 五段随机间隔观察写回。观察阶段最多读取缓存 6 次、纯等待总计 `750ms–1s`；加上 `GetUserProfile` 进入 singleflight 前的首次缓存读取，单个请求在该竞争分支最多读取 7 次。仍未命中时返回重建等待超时，禁止绕过锁并发回源。
- 允许短时等待的普通临界区使用 `WithLock`：首次加锁立即请求，失败后最多重试 5 次，基础等待依次为 `100/200/300/400/500ms`，每轮叠加 `0–100ms` 随机抖动，对应实际区间 `100–200/200–300/300–400/400–500/500–600ms`，纯退避总和为 `1.5–2s`。统一加锁总超时为 `3s`，调用方更短的 context deadline 优先生效；Redis 在 deadline 内正常响应且持续竞争耗尽时返回锁竞争错误，Redis 操作或整体等待超时时保留 context/基础设施错误。
- 一个 `redis.UniversalClient` 只适配为一个 redsync pool，仲裁数为 `1`；Redis Cluster 的分片节点不是多套相互独立的主节点仲裁。该互斥不能替代数据库事务、唯一约束、条件更新或 fencing token，任何锁失败都不能绕过保护直接执行最终写入。
- 写后优先 `RenewByKey`，动态 UUID 场景使用 `RenewByUUID`；不要通过通配扫描刷新。
- 锁释放和认证状态迁移使用校验 owner/旧值的 Lua 原子脚本。

新增缓存必须说明 key 组成、值结构、TTL、空值、回源、击穿、写后失效、跨服务共享和故障降级。

## 8. 认证与会话扩展

### 8.1 JWT 与 session

- JWT 使用 HS256，包含十进制字符串 `sub`、稳定 `sid`、唯一 `jti`、`username`、`iss`、当前 `app_id` 和正整数 `auth_version`。
- 鉴权依次校验 token、issuer、AppID、Redis session/版本和主库用户状态。
- session 使用同槽 Redis Hash 与 ZSET 过期索引；刷新在同 `sid` 下 CAS 完整旧 token 并生成新 `jti`。
- 退出只删除当前 `sid`；全量失效必须先在数据库事务中单调递增 `user.auth_version`，提交后再调用运行态同步推进 Redis 版本并清空会话。
- 旧版本同步不能覆盖新版本，版本栅栏 TTL 至少覆盖 JWT 最长存活期。

修改认证链路时必须同步接口文档、业务码、Redis Lua/Key、认证风控事件和 Admin 运行态同步契约。

### 8.2 限流

- 登录按 IP 和登录身份两个维度限流，身份包含 `username/email/phone` 类型和值。
- 注册按 IP 限流；生产开放注册时必须启用。
- 计数、窗口 TTL 和锁定使用同槽 Lua 原子维护。
- 启用参数受启动校验限制，不能设置无界窗口或锁定。
- Redis 不可用时按安全设计失败关闭，不能静默绕过认证限流。

## 9. ID 生成

### 9.1 Snowflake

- 使用 `github.com/bwmarrin/snowflake`。
- 生产多实例默认从 `snowflake.redis` 共享租约池分配 `0..1023` node ID。
- Admin/API 同一部署使用相同 `scope`，业务唯一域由 `NextID(namespace)` 的 namespace 区分。
- `snowflake.redis.namespaces.<namespace>.node_count` 可限制业务可竞争节点数；所有调用同一 namespace 的服务必须一致。
- `worker_id` 只用于手工强管控，不能与 Redis 自动分配同时启用。
- 租约丢失后只停止对应 namespace 发号，避免重复 ID。
- 本地发号期限按申请或续租发出时刻加 `lease_seconds - renew_interval_seconds` 计算；续租回包阻塞也会到期拒绝发号，旧回包和旧实例关闭不能覆盖新绑定。
- 正常停机先停止本地发号，再刷新一个完整 `lease_seconds` TTL；租约 key 在隔离期内不删除，防止不同主机时钟偏差下立即复用同一 node ID。

### 9.2 Segment

高吞吐业务可在 `snowflake.segment.namespaces` 按 namespace 启用 Redis Segment：

- 每次 `INCRBY` 申请本地号段，不做 per-ID Redis 队列。
- 进程崩溃可能产生空洞，但不能产生重复 ID。
- 适合唯一性优先、不依赖雪花时间位的订单号。
- `step` 过小会增加 Redis 申请频率，过大会增加故障空洞，必须按峰值压测。

Snowflake/Segment 都属于启动期能力，热加载变化只标记 `restartRequired`。

## 10. 配置扩展

### 10.1 启动期配置

新增配置字段时同步 struct、JSON/YAML tag、样例、默认值、normalize、validate、热加载指纹和文档。以下能力默认属于启动期：

- 公网 `RestConf` 与 `internal_server`。
- `app_id/app_key/instance_id/trusted_proxies`。
- JWT secret、有效期和 issuer。
- `security`、Collector、MySQL、Redis、Snowflake、observability。
- 路由、组件和 listener 注册。

热加载发现这些变化时保留当前值，并返回明确 `restartRequired/restartReason`；不能更新快照后声称已经生效。

### 10.2 运行期配置

- `config_files.runtime` 只合并 `runtimefile:sectionSpecs` 声明的配置段。
- API 已保留 `sys_config` Model、初始化 DDL、table-cache 目标、`SysConfigLogic`、`SysConfigKey` 和类型化 getter；当前没有生产业务调用方，不得把基础能力描述为已启用。
- 新增全局业务运行期配置时复用现有实现，先登记 `SysConfigKey`，再使用 `GetBool/GetInt/GetString/GetFloat/GetObject/GetArray`，并补真实调用方、缺失/非法值、缓存一致性和故障降级测试。
- `GetCachedValue(uuid)` 只用于真实动态 UUID 场景。
- 缓存 Object/Array 内的数字返回 `json.Number`，避免大整数和长小数被舍入；独立 Integer/Float 仍返回 `int`/`float64`，默认容器保留调用方声明类型。容器不接受 `null`、类型不符或尾随 JSON。
- 表名固定 `sys_config`，不新增 `api_sys_config`。

### 10.3 生产硬校验

`Mode=pro` 是唯一生产规范值；`prod/production` 和大小写、首尾空白变体均在启动期拒绝。生产模式至少校验：

- JWT 和 Ops token 不是占位值并满足长度。
- 登录限流与 Collector 已启用。
- Redis TLS 不跳过证书校验。
- `trusted_proxies` 只包含真实 LB/Ingress IP 或 CIDR，不能信任全网段。
- internal listener 绑定明确私网 IP；跨主机配置 mTLS。
- 安全密钥版本、灰度 salt、AES/RSA 材料和开关合法。

## 11. Collector 事件

API Collector 只向 Kafka 投递结构化事件，不在请求链路落 DB 或写业务 Redis。

新增 bizType：

1. 定义稳定事件契约、action/reason 枚举和脱敏规则。
2. 配置 `collector.tasks.<bizType>.topic`，与 Admin 消费方使用同一 Topic。
3. 选择稳定 partition key，保证需要的局部顺序。
4. 调用 `Collector.Enqueue`，明确失败是否阻断主业务。
5. 补成功、失败、超时和 payload 上限测试与指标。

边界：`eventId<=64` 字节、`bizType<=100`、`partitionKey<=128`、JSON payload<=60 KiB、完整消息<=64 KiB。认证风控事件单次投递最多占用请求链路 100ms，best-effort 失败不改变认证结果；payload 禁止密码、token、明文用户名或明文 IP。

## 12. 启动组件与生命周期

MySQL、Redis、Snowflake、Collector 等核心组件先在 `internal/bootstrap/components:DefaultSpecs` 声明，再注册到 `svc.ComponentRegistry`：

- `Check` 决定 `/api/ready` 如何探测。
- `Close` 决定服务停止时如何反向释放。
- 组件名称、错误码和启用条件必须唯一、稳定。
- 不在 `HealthLogic` 临时添加依赖分支，也不在 main 重复关闭资源。

轻量运行时扩展放在能力归属包 `RuntimeRegistrySpecs`，bootstrap 只汇总。清单项必须标明“生产已启用”或“基础能力/未激活”：新增 Collector bizType 只有 Topic、真实 `Enqueue` 调用方和失败语义接通后才算启用；新增 sys_config key 只有业务读取链路、缺失/非法值和缓存一致性测试完成后才算启用。基础能力保留其契约和聚焦测试，但不得用清单项冒充生产调用链。

## 13. 内网运维接口

所有 `/internal/` 路由：

- 只注册到 `internal_server`，公网 listener 不得出现。
- 校验本机/私网来源，可用 allowlist 进一步收窄但不能放行公网。
- 使用 `X-Ops-Token`、时间戳、nonce、body SHA256 和 HMAC。
- HMAC 绑定 method、完整 request URI、timestamp、nonce 和 body digest。
- nonce 通过 Redis `SET NX` 覆盖完整剩余窗口；Redis 不可用时失败关闭。
- 生产跨主机监听绑定私网 IP 并使用服务端 mTLS。

新增内网接口仍要有 RouteMeta、业务码、接口文档、测试和审计边界；“内网”不是省略契约的理由。

## 14. 文档与前端同步

每个接口文档必须包含：

- method/path、访问边界和适用调用方。
- 请求头、path/query/body 字段及默认值、上限、单位、空值。
- 请求签名、请求加密、响应签名和响应加密字段。
- 成功和关键失败示例。
- 业务码、HTTP 状态、触发条件和调用方处理建议。
- 幂等、重试、分页、限流、缓存和安全注意事项。

接口变化同步前端 TypeScript 类型、route policy、业务码/i18n 和安全向量。没有前端仓库时也要维护 `route_security_manifest.json` 作为稳定交接资产。
