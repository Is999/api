# 认证安全指标与告警

本文档用于 `api` 认证、签名和加解密链路的生产观测。API 侧只负责把脱敏事件投递到 Collector Kafka，并观测投递成功率；认证安全细分指标由下游消费侧按 `auth.security` 事件聚合。

## 指标

`api_collector_kafka_publish_events_total{result}` 由 API Collector 统计：

| 标签 | 说明 |
| --- | --- |
| `result` | Kafka 投递结果：`success`、`failed` 或 `unknown` |

该指标只反映 API 到 Kafka 的发布结果，不等于登录成功率或安全攻击量。认证细分指标必须由下游消费 `auth.security` 事件后聚合；Kafka 发布故障期间，事件观测可能缺失，但 API 业务链路仍按各调用点的 best-effort/阻断约定执行。

`api_auth_rate_limit_cleanup_failures_total{action}` 统计登录会话和最后登录信息已经提交后，IP 或登录身份限流 Key 清理失败的次数。`action` 只允许 `login_ip`、`login_identity` 和代码兜底 `unknown`，不会包含用户名、IP 或其它高基数数据。该指标递增时客户端仍收到成功登录响应，运维需检查 Redis 写可用性并确认限流 Key 在 TTL 到期后自动回收。

## 分类

`auth.security` Kafka 事件中的低基数字段：

| 字段 | 典型值 | 处理方向 |
| --- | --- | --- |
| `action` | `login_failed`、`auth_failed`、`security_failed` | 关注认证、登录态和安全链路异常分布 |
| `reason` | `signature_failed`、`request_decrypt_failed`、`security_key_unavailable` | 下游消费侧按原因聚合告警和报表 |
| `app_id` | 当前站点命名空间 | 多站点隔离观察 |
| `route` | 稳定路由别名 | 定位异常接口 |
| `user_id` | 十进制字符串 | 保留雪花 ID 全精度；下游禁止按 JSON number 解析 |

高基数字段 `user_id`、脱敏用户名/IP/session 哈希、trace 只用于单事件排障，不得直接作为 Prometheus label。指标 label 只使用稳定低基数维度，例如 `result/action/reason/app_id/category`；`route` 仅在确认集合受控时进入下游报表。

## 告警建议

以下 PromQL 阈值是示例，生产环境应按实际流量基线调整。

```promql
sum(rate(api_collector_kafka_publish_events_total{result="failed"}[5m])) > 0
```

API Collector 投递失败应告警，优先排查 Kafka broker、Topic、ACK、网络和 `collector.tasks` 配置。

```promql
sum(rate(api_auth_rate_limit_cleanup_failures_total[5m])) > 0
```

认证限流清理失败应告警，优先核对 Redis 连通性、超时和当前登录错误率；Key 自带窗口或锁定 TTL，不需要批量 `SCAN/KEYS` 清理。

```promql
sum(rate(api_collector_kafka_publish_events_total{result="success"}[5m]))
```

用于确认认证安全事件进入 Kafka。当前 Admin 消费侧按 `action/reason/app_id/category` 聚合低基数指标，`route` 仅保留在事件中辅助排障。

### 告警分级

| 级别 | 示例条件 | 首要动作 |
| --- | --- | --- |
| P1 | 多站点登录成功量突然归零，且 `/api/ready` 非 2xx 或任一 enabled 组件为 failure | 依次核对实例存活、网关 upstream、`/api/ready` 的 MySQL/Redis/Collector 字段和连接错误，再结合安全事件判断；不能从事件计数单点下结论 |
| P1 | `security_key_unavailable` 持续出现并影响主要认证路由 | 停止错误密钥发布，核对启动配置、版本选路和密钥文件，准备回滚并重启 |
| P2 | Kafka `failed` 在 5 分钟窗口持续大于 0 | 检查 broker、Topic、ACK、网络和 Collector 配置 |
| P2 | 认证限流清理失败指标在 5 分钟窗口持续大于 0 | 检查 Redis 写链路与超时；禁止在线全库扫描清理 Key，等待 TTL 或按已知精确 Key 处置 |
| P2 | `signature_failed` 或 `request_decrypt_failed` 显著偏离同站点基线 | 区分客户端版本漂移、密钥灰度错误和攻击流量 |
| P3 | 单 route/单版本少量安全失败 | 用 trace 与脱敏事件核对客户端输入，观察趋势 |

阈值必须按站点、流量和时间段建立基线。不要把示例 PromQL 直接作为全站固定阈值，也不要因为攻击峰值自动放宽签名、加密或限流。

### 推荐看板

- Collector 发布成功、失败和失败率，按实例与 `app_id` 查看。
- 认证 action/reason 趋势，区分登录失败、会话失效、限流和安全链错误。
- 登录/注册请求量、HTTP 状态、业务码和 P50/P95/P99 延迟。
- Redis、数据库、Kafka readiness、错误率和连接池状态。
- 密钥版本与客户端版本分布，用于定位灰度不一致。
- 告警发送成功、被聚合次数和静默窗口。

## Lark 运行异常告警

`alert.lark` 用于把 API 自身运行异常推送到 Lark 群机器人。该通道只覆盖和前台服务可用性相关的异常，不引入 admin 的后台任务、周期任务、日报或工作流告警。

当前会触发 Lark 的场景：

- API 启动装配失败、路由注册失败、HTTP Server 创建失败。
- API 平滑停止时资源释放或 tracing 关闭失败。
- `config.yaml` 热加载失败，包括文件指纹读取、配置解析、取消和未绑定配置文件。
- Collector Kafka Topic 未配置或投递失败。

配置示例：

```yaml
# API 外部告警通道；本段变更需重启生效。
alert:
  # Lark 发送端读取以下配置，关闭时不创建发送器。
  lark:
    # 启用 Lark；未传为 false，启用后必须提供 webhook。
    enabled: true
    # webhook 文件引用，与 webhook_url 二选一；内容仅在启动时加载，禁止提交真实地址。
    webhook_url_ref: "/run/secrets/api/lark_webhook_url"
    # 可选签名密钥文件，与 secret 最多选一个；两者均空时不附加机器人签名。
    secret_ref: "/run/secrets/api/lark_secret"
    # 单次 HTTP 超时秒数，0 取 5，允许 1–30；负值或超过 30 拒绝启动。
    timeout_seconds: 5
    # 是否在告警中 @所有人，未传为 false。
    at_all: false
    # 错误摘要最大字节数，0 取 800，负值拒绝启动。
    max_error_bytes: 800
```

说明：

- 告警卡片中的环境读取顶层 `Mode`，不要额外维护第二套环境字段。
- `webhook_url` 与 `webhook_url_ref` 必须二选一；`secret` 与 `secret_ref` 最多选择一个。明文值和文件引用同时出现、首尾带空白时启动直接失败。
- 同一低基数异常指纹默认按 5 分钟窗口合并，窗口内重复触发会计入下一次告警的窗口触发次数。
- `alert.lark` 属于启动期发送端配置，热加载变更会提示需重启，当前进程继续使用旧配置。

## 排障边界

- `request_decrypt_failed` 和 `signature_failed` 多数是客户端请求、字段顺序、秘钥版本或 trace 参与签名不一致，应从 Kafka 消费侧聚合趋势。
- `security_payload_too_large` 表示请求签名、请求加密、响应签名或响应加密字段超过安全链路上限，不应简单扩大上限；优先减少参与字段。
- `security_key_unavailable` 属于服务端密钥注册表、版本选路或材料问题，先核对进程启动时的 `security.secret_key`、灰度路由和 AES/RSA 解析日志。请求期不会读取密钥引用文件，文件内容变更后必须重启；API 也不从 `sys_config` 回源安全密钥。
- `response_sign_failed`、`response_encrypt_failed` 属于后端响应处理问题，先检查 RouteSecurityPolicy、接口文档安全字段和实际响应结构是否一致。
- `/api/metrics` 必须仅允许内网、网关白名单或 Prometheus 来源访问，禁止公网直接暴露。

## 事件处置流程

1. 确定 `app_id`、环境、时间窗口、route、action/reason 和影响比例。
2. 先用 HTTP 业务码与 ready/依赖指标判断是业务、安全链还是基础设施故障。
3. 通过脱敏事件的 trace 查 API 最外层日志；禁止在日志平台搜索密码、token 或明文身份字段。
4. 签名/加密异常时比较同一客户端版本和密钥版本，并按[前端安全策略同步与联调指南](角色文档/后端开发/前端安全清单同步.md)核对 manifest 与测试向量。
5. session/auth_version 异常时核对 JWT claim、Redis Hash/ZSET/版本键和主库用户状态，不能只删除 Redis key。
6. Collector 故障时确认业务是否按 best-effort 继续；恢复后不能假设 Kafka 自动补齐故障窗口内所有事件。
7. 处置结束后记录数据缺口、受影响调用、是否需要补偿、阈值调整和永久修复。

## 隐私与保留

- 认证事件禁止密码、token、密钥、明文用户名、手机号、邮箱和 IP。
- 用户名/IP/session 只保存不可逆或受控脱敏值；盐和算法由统一 helper 管理。
- `user_id` 保持十进制字符串，权限和日志系统按敏感标识控制访问。
- 下游存储必须配置保留期、访问审计和删除策略；不能因为“安全分析”无限期保留高基数身份数据。
- Lark 告警只发送低基数摘要、trace 和脱敏上下文，不附完整事件 payload。

## 验证与演练

发布认证、安全策略或 Collector 变更前至少验证：

- 成功、失败、超时三类 Kafka 发布指标准确递增。
- 认证事件 action/reason 与业务码和调用阶段一致。
- payload 不包含密码、token 或明文身份/IP。
- Kafka/Redis 故障时主业务遵守预定 best-effort 或失败关闭语义。
- Lark 聚合、超时和密钥引用生效，告警自身失败不会递归放大。
- `/api/metrics` 网络边界正确，标签集合无高基数泄漏。

修改 Collector 发布、认证安全事件或启动注册时，分别运行 Collector 归属包、认证 handler/logic 和 bootstrap manifest 测试；共享事件结构变化时三组测试全部运行。交付说明列出当前阈值来源、生产指标基线和是否调整，不能只写“相关测试已通过”。
