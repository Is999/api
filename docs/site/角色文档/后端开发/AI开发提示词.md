# AI 开发提示词

复制下面的提示词，并在末尾追加本次任务。完整细则见根目录 `AGENTS.md` 和 [AI 开发规范](角色文档/后端开发/AI开发规范.md)；提示词用于明确执行重点，不能替代规范或覆盖用户最新的明确要求。

```text
你正在参与 api-go 开发，请按以下要求完成我给出的任务。

一、最高优先级：代码质量与可维护性

业务正确、安全、数据完整性和资源边界不可退让；在此前提下，代码简洁、逻辑清晰、代码易阅读易维护是所有实现的最高优先级，不是功能跑通后的可选润色，也不能以测试通过替代。

- 代码实现必须达到专业资深的高级开发者标准：命名准确、风格统一，主流程按业务顺序展开；不出现 AI 式模板堆砌、无职责包装、过度抽象、重复查询和重复判断。
- 阅读和维护门槛以初级开发者也能轻松上手为目标：通过主流程、就近注释和测试理解已实现的需求、业务规则、关键分支与失败策略，定位修改及回归位置，不依赖作者口头解释或隐含约定。
- 每个新增目录、接口、结构体、状态、分支和 helper 都要有当前需求或真实调用方；无独立职责的转发直接内联，不为假设性扩展预建层级。不能为少写几行代码删除必要的锁、原子性、幂等、超时或取消边界。

二、注释重点：一个逻辑点，一条就近说明

- 新增或重构的声明按规范补中文注释，说明职责、数据来源、单位、空值或约束；方法注释解释该方法的业务职责与调用边界，不罗列内部步骤。
- 方法内部的查询准备、条件分支、状态变更、写入、重试和资源释放，凡有业务原因、先后顺序、并发约束或失败策略，都在对应步骤或分支前说明。三个逻辑点分别写三条就近注释，不在方法开头集中概括；一句话能说清楚就不写成长段，不逐行翻译普通赋值和显然的错误返回。
- 修改项目自有 YAML 时，固定字段在正上方以相同缩进补中文注释，写清消费组件、用途和源码实际存在的取值、默认值、单位、热加载或重启约束；父节点概述不能代替子字段说明。

三、开始前：先读现状，确定执行边界

- 完整阅读当前生效的 AGENTS.md、docs/site/角色文档/后端开发/AI开发规范.md，以及目标入口、调用方、测试和文档。以当前工作区（包括已暂存内容）为事实源，旧结论须重新对照当前源码，不覆盖用户已有改动。
- 使用 $standard-development-flow，并按 AGENTS.md 的触发条件选专项 skill。只读复核、解释或方案任务不得修改代码、配置、SQL、脚本或文档；需求有歧义或涉及接口、数据、权限、安全、缓存、迁移、大查询时，先给源码证据、方案和影响边界，按 $requirement-intent-gate 确认后实施；已确认且范围未变的事项不重复询问。
- 全仓任务须逐文件覆盖源码、配置、SQL/Lua、脚本和文档，记录已检查及未覆盖范围；不能用少数文件、注释数量或测试通过冒充全仓完成。普通需求只改需求、实际同步面及验证修复涉及的文件。

四、实现时：走通真实入口，不留半成品

- 从实际 HTTP、消息或命令入口追到响应、持久化及外部副作用，检查成功/失败分支、配置注册、鉴权和资源释放；跨服务变化还要检查 Admin 写入与 API 读取之间的配置、会话和缓存约定。只有 helper、注册清单或 happy path 不算接入完成。
- 只维护当前唯一基线；不保留旧字段别名、历史兼容分支、双写双读或仅为隔离旧格式而新增的版本前缀。同步当前调用方、样例、测试和文档；不能把现有部署模式、密钥业务版本、故障恢复或尚未启用的基础能力误当成历史兼容删除。
- 优先复用当前分层和成熟依赖；新增抽象、目录、依赖或框架前，说明当前问题、替代方案、收益、影响和验证方式，确认后再引入。运行期失败返回受控错误，禁止用 panic/Fatal/Exit 终止服务；错误按规范包装并由最外层记录，失败分支释放已持有资源。
- 数据库优先使用 GORM，核对往返、索引、扫描、批量、超时和并发；不需要跨语句原子性或一致性快照时不额外包事务，不能把一次批量调用或 Hook 当作一条原子 SQL。
- 必须使用事务时，解析、校验、计算、整理和独立查询前置，只把原子读写、锁定读取与提交条件重验留在事务内；不在事务里做远程请求、Redis/MQ、文件处理、等待或退避重试。
- 事务必须轻量且有行数、执行时间和锁等待边界；允许独立提交才拆成有界小批，整体原子性不可拆坏，超预算先限制规模或确认新方案。提交后副作用沿用既有失败恢复路径；没有前后测量，不宣称性能已提升。
- 数据库结构和基线数据变化修改完整初始化资产，不新增碎片化版本迁移；存量库 SQL 只放在被忽略的 data/sql-changes/<change-id>/，交 DBA/运维执行，不暂存、不提交。
- 按源码 diff 和调用方搜索确定契约、配置、数据库、缓存、文档及运维影响，逐项记录修改文件与验证依据；不机械填写全部同步面，也不以“相关内容已同步”代替实际检查。

五、验证与交付：结论必须对应最后一次修改

- Go 改动执行 gofmt，优先运行 go test ./...；并发、依赖或启动链路变化补对应 Race、真实集成和候选进程冒烟。纯文档变更检查路径、链接、导航、复制入口和命令依据。验证受阻时运行可执行的受影响范围，列明未覆盖项、原因和补跑命令。
- Bug、故障测试和阻塞按“正常逻辑缺陷”“极端运行条件”“验证环境阻塞”分栏，逐项写触发条件、证据、期望与实际、影响、是否修复和后续责任；极端条件再区分处理符合预期或存在韧性缺陷，不能把本地缺服务当成代码 Bug，也不能当成验证通过。
- 最后一次修改后执行 git diff --check、git status --short；存在暂存内容时执行 git diff --cached --check。本轮新增交付文件须精确暂存，不混入无关文件、本地数据或 DBA SQL；未经要求不提交、不推送、不改历史。
- 使用 $implementation-closure-review 和 $release-handoff-guard 收口。交付列出修改内容、真实入口与同步结果、验证命令及执行目录和结果、未验证路径、剩余问题，以及迁移、回填、缓存失效、重启或补偿等人工动作；区分已验证、未验证和受阻，不承诺“没有 Bug”或用“生产可用”概括未检查项。
```
