# 接口文档统一规范

本文档定义 `api` 前台 API 文档的统一书写样板。所有接口按“请求示例、字段说明、响应示例、响应字段说明、data 内部字段”的结构维护。

> **AI 开发必读**：AI 新增或修改接口文档前，必须先阅读仓库根目录 `AGENTS.md` 和 [AI开发规范](角色文档/后端开发/AI开发规范.md)，并同步检查业务码、多语言文案、路由元数据和测试。

## 通用响应结构

### 响应示例

```json
{
  "status": true,
  "code": 1,
  "message": "操作成功",
  "data": {},
  "traceId": "0af7651916cd43dd8448eb211c80319c",
  "spanId": "b7ad6b7169203331"
}
```

### 响应字段说明

| 字段 | 类型 | 是否必须 | 默认值 | 字段解释 |
|------|------|----------|--------|----------|
| status | bool | 是 | false | 状态: true 成功, false 失败 |
| code | int | 是 | 0 | 业务状态码，不同业务错误返回不同状态码 |
| message | string | 否 |  | 当前语言下的响应消息，受 `Accept-Language` 影响 |
| data | object/array/null | 否 |  | 业务响应数据 |
| traceId | string | 否 |  | 链路追踪 ID，便于日志检索 |
| spanId | string | 否 |  | 当前服务 span ID |

## 通用请求头

| 字段 | 类型 | 是否必须 | 默认值 | 字段解释 |
|------|------|----------|--------|----------|
| Authorization | string | 条件必填 |  | 登录态接口必填，格式 `Bearer <token>` |
| Content-Type | string | 条件必填 | application/json | 非空 JSON 请求体必填合法 `application/json` 媒体类型，允许大小写变体及 charset 参数；表单请求只允许 `application/x-www-form-urlencoded` |
| Accept-Language | string | 否 | zh-CN | 国际化语言，支持中文和英文 |
| X-Trace-Id | string | 否 |  | 请求链路追踪 ID；提供时必须是 32 位小写十六进制，签名请求还必须与 `traceparent` 中的 trace-id 一致 |
| X-Timestamp | string | 条件必填 |  | 秒级 Unix 时间戳；开启签名后必填，参与签名并校验 5 分钟时间窗口 |
| X-App-Id | string | 条件必填 |  | 配置 `security.secret_key` 后必填，值为 base64 后的 `app_id` |
| X-Signature | string | 否 | R | 签名方式：`R` RSA-SHA256、`H` HMAC-SHA256；其它值一律拒绝 |
| X-Crypto | string | 否 | A | 加解密方式：`A` AES-256-GCM、`R` RSA-OAEP-SHA256；其它值一律拒绝 |
| X-Cipher | string | 条件必填 |  | 请求加密字段列表，禁止使用 `cipher` 整包加密 |
| X-Key-Version | string | 否 |  | 指定秘钥版本；为空时按稳定/灰度配置选路，最长 64 位且不能包含空白或通配符 |
| X-Gray-Key | string | 否 |  | 灰度秘钥分桶键，通常使用用户 ID 或设备 ID |

时间戳接受前后五分钟偏差；防重放记录保留到该时间戳的完整有效窗口结束，客户端时间领先时仍不能重复提交同一请求。

## 签名与加密字段

- 接口文档必须列出参与请求签名、响应签名、请求加密和响应加密的具体字段；没有业务签名字段但仍启用签名时，写明仅签 `appID`、`traceID`、`timestamp`，不能标记为“不参与签名”。
- `R` 和 `H` 使用 `v2` 长度前缀协议：先编码 AppID、traceID、timestamp，再按字段 ASCII 顺序追加字段名和稳定字段值；组合模式的字段值是最终密文，所有长度按 UTF-8 字节计算。
- 未知签名方式直接拒绝，不做兼容降级。
- `sign_status=1, crypto_status=0` 允许单独签名；`crypto_status=1` 时 `sign_status` 必须为 `1`，否则应用拒绝启动。
- 组合模式下每个加密字段以相同点路径列入签名字段；客户端请求先加密再签名，服务端先验签再解密；响应反向执行，客户端先验签再解密。
- `json:` 只标记加密字段的 JSON 编解码方式，不是业务字段名。例如加密字段为 `json:payload` 时，签名字段必须为 `payload`，并对该字段的最终密文签名；解密保留 JSON 数字精度且拒绝尾随第二个 JSON 值。当前内置路由未启用此扩展能力。
- 请求和响应签名禁止默认使用 `*` 对完整请求体、完整响应 `data`、大结构体或分页列表整体签名。
- 请求和响应加密禁止默认使用 `cipher` 整包加密，只允许声明字段级路径。
- 签名和加密优先覆盖 token、金额、订单号、手机号、邮箱、二次校验字段等重要数据，避免拖慢大响应解析。
- 单个接口参与签名或加密的字段最多 8 个；普通安全字段最大 4KB，`json:` 小对象最大 8KB。
- 安全中间件读取请求体最多 64KB；更大的业务负载应走专用上传、异步任务或拆分字段。
- 参与签名或字段解密的非空请求体必须声明业务解析器实际支持的媒体类型；JSON 使用 `application/json`，表单使用 `application/x-www-form-urlencoded`。缺失、格式错误或其它媒体类型直接拒绝，避免验签内容与 handler 实际解析内容不一致。
- 内网 Ops HMAC 接口的非空请求体只允许 JSON，并必须声明 `Content-Type: application/json`；空请求体不要求 Content-Type。

### 算法编码契约

- `H` 签名：对 `aes_key` 的 UTF-8 字节做 HKDF-SHA256，`salt` 为空、`info` 为 `field-signature:hmac-sha256:v1`，派生 32 字节子密钥；对 `v2` 签名串计算 HMAC-SHA256 后使用标准 base64。
- `R` 签名：密钥至少 2048 位；对 `v2` 签名串的 SHA-256 摘要使用 RSA PKCS#1 v1.5 签名，结果使用标准 base64；该类型只用于签名，字段加密不使用 PKCS#1 v1.5。
- `A` 加密：对 `aes_key` 做 HKDF-SHA256，`salt` 为空、`info` 为 `field-encryption:aes-gcm:v1`，派生 32 字节 AES 子密钥。每个字段生成独立 12 字节随机 nonce，AAD 固定为同一 `info` 字符串，输出为标准 base64(`nonce || ciphertext || 16-byte tag`)。
- `R` 加密：密钥至少 2048 位；固定使用 RSA-OAEP-SHA256，label 为 `field-encryption:rsa-oaep:v1`；明文按 `keyBytes-2*32-2` 分块，密文按固定 `keyBytes` 块拼接后整体使用标准 base64。
- 标准 base64 必须可往返且不得包含首尾空白；AES-GCM 标签、OAEP 解码、密文长度或 base64 任一失败都按同一请求安全失败契约返回。

## 安全失败业务码

安全链路失败只返回脱敏后的业务码和多语言文案，真实失败阶段只进入日志、trace 和风控事件。验签、密文格式或请求解密失败统一返回 `20008/401`，避免客户端通过差异响应判断解密阶段。

| 业务码 | HTTP | 中文文案 | 场景 |
|--------|------|----------|------|
| 20006 | 400 | 安全 AppID 无效 | `X-App-Id` 缺失或格式错误 |
| 20007 | 500 | 安全秘钥不可用 | 秘钥配置、版本或缓存不可用 |
| 20008 | 401 | 请求安全校验失败 | 验签、密文格式、解密或解密后字段校验失败 |
| 20009 | 413 | 安全字段超过限制 | 请求体、字段数量、字段长度或复杂结构超过轻量处理上限 |
| 20010 | 403 | 加解密链路未启用 | 客户端声明密文但当前应用关闭加解密 |
| 20011 | 500 | 响应签名处理失败 | 响应回签字段声明或签名生成失败 |
| 20012 | 500 | 响应加密处理失败 | 响应加密字段声明、编码或加密失败 |

## 链路追踪与排障

- 后端会将 `trace_id`、`span_id`、`uid`、`route`、`node` 写入访问日志和错误日志。
- 同一错误链路只在 handler、中间件或健康检查顶层打印一次 error 日志。
- 多实例部署时登录态按用户保存在同槽 Redis Hash，稳定 `sid` 的过期索引使用 ZSET，认证版本使用有界 TTL String；有会话时其 TTL 与最晚会话同步，全量失效时至少覆盖 JWT 最长存活期。排障时可结合 `uid`、`sid`、`jti`、`auth_version` 和 `trace_id` 查询。
- Redis session TTL 不超过 JWT 过期时间；JWT `sub` 使用十进制字符串承载雪花用户 ID，`sid` 在一次登录会话内稳定，`jti` 每次刷新都唯一，`auth_version` 使用正整数，雪花 ID 和认证版本禁止经 JSON 浮点数解析。创建、校验、刷新和失效均通过同槽 Lua 原子处理，刷新对同 `sid` 执行完整旧 token CAS；退出原子删除并标记当前 `sid` 已撤销，失败补偿不能将其恢复，详见[认证接口](前台系统/认证接口.md)。每个用户最多保留 8 个有效会话。
- admin 敏感变更必须在数据库事务中先单调递增并提交 `user.auth_version`，再携带新版本调用运行态同步接口。API 原子推进 Redis 认证版本并清空会话 Hash/ZSET，旧版本不能覆盖新版本；请求期在 Redis 原子校验后还会查询主库状态和认证版本，关闭数据库提交到 Redis 清理之间的并发窗口。
- 注册、登录、刷新、退出、登录态鉴权失败、限流和用户级 session 失效会 best-effort 投递 `auth.security` 认证风控事件；payload 只保留脱敏哈希和链路字段，投递最多阻塞 100ms，API 侧通过 `api_collector_kafka_publish_events_total{result}` 观察投递结果。
